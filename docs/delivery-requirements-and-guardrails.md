## 0. 读法与四条使用纪律

1. **需求（DR）** = 要做什么；**护栏（G）** = 靠什么保证做对、且不回退。**没有对应护栏的需求 = 不可宣称完成**。
2. 每条需求的状态**如实标注**：`✅ 已达成` / `🟡 部分` / `⏳ 零代码` / `📄 仅文档就绪`。**"文档就绪"不等于"已做"**。
3. 编号**只追加不重排**（守 `dev-doc-status.md` R5）。作废的需求**不删**，标 `❌ 作废` 并写理由——防止"曾经决定过又忘了"。
4. **本文的 ✅ / 🟡 会过期，别拿它当结论**——护栏大半是 `xfail` 骨架，**pytest 全绿 ≠ 护栏在拦**。
   判定一律以机器输出为准，见 §0.1。

### 0.1 开工自检（怎么拿到"此刻的真话"）

```bash
cd backend && uv run python scripts/check_startup_readiness.py
```

脚本**解析测试源码**（不跑测试，秒级完成），把护栏分成三档：

| 输出档位 | 含义 | 该怎么办 |
|---|---|---|
| `[OK]` 已生效 | 测试红就是它拦的 | 正常开发；改坏了它真的会拦你 |
| `[~~]` 部分生效 | 一半在拦、一半挂着 | **挂着的那一半所管的需求不得宣称完成** |
| `[--]` 挂起 | CI 绿，但没在拦任何东西 | 对应 DR **一律不得宣称完成** |

另外**注意两类特殊条目**，它们最容易出事：

- **⚠️ 恒绿失效**（纪律 **R-9**）：校验对象本身不存在（如 `plugins/`、`deploy/variants/`、
  License 子系统）⇒ 即便删掉 `xfail` 也只是空跑。**先让对象真的存在，转正才有意义。**
- **🛡 反向守卫**：必须**始终通过**的测试（如 `test_g21_production_sqlite_guard_still_present`）。
  删掉它等于拆护栏——清理 SQLite 时最容易把它当成"残留"一起删掉。

脚本还输出**开工地雷**（是否切 PG、`users` 表是否建、License 是否零代码……），
这些一旦判断错，整段工作会白做。

> **为什么不做成人工 checklist**：清单要靠"记得去看"，而护栏状态每次提交都在变。
> 所以它同时写进了**三处不依赖人去记的地方**——根 `CODEBUDDY.md` §开工自检、
> `backend/CODEBUDDY.md` §常用命令、以及 CI 的 backend job（每次提交把快照打进日志）。

### 2.2 待建护栏（**本轮新增，DR 的判据**）

> **关于「骨架已就位」与 `xfail(strict=True)`（先读这段）**
>
> 护栏是"**验证需求已完成**"的判据 ⇒ **需求没做时，护栏建了必然失败**。
> 若此刻建成硬断言，CI 立刻变红——那不是护栏，是噪音，而且很快会被人顺手关掉。
>
> 因此需求未完成的一律以 **`xfail(strict=True)` 骨架**就位：
>
> - **现在**：断言失败 ⇒ **XFAIL**（CI **保持绿**，`-rx` 把原因逐条打进日志）；
> - **需求达成**：断言通过 ⇒ XPASS ⇒ strict **判为失败**，强制来人摘掉 `xfail` 标记 ⇒ 转常驻门禁。
>
> **摘标记的时刻 = 该需求被宣称完成的时刻。** 谁摘，谁就在声明"这条已达成"。
> 这样护栏能**先于需求就位**，且"哪些护栏还没真正生效"始终写在日志里——
> 与 CI 里"本地独占用例单独跑一遍只为让原因可见"是同一条纪律，不留在沉默中。

## 7. 版本语义（**2026-10-01 定义 · 兑现商业承诺的前提**）

> **为什么必须先定义它**：ADR-0007 §3.8 承诺「**升 V2.0 才需重做插件**」，而 **G-11 签名快照**的判据是「打补丁 ⇒ 快照逐字相同」。
> **若"什么是补丁"没有定义，这两条都落不了地**——承诺无法兑现、快照无法判。实测当前 `app_version = 1.6.0`（`config.py:92`）。

### 7.1 三段式定义

`app_version` = `MAJOR.MINOR.PATCH`

| 段 | 递增时机 | 插件影响 | 机械判据 |
|---|---|---|---|
| **MAJOR**（第一位） | 架构代际更替 / **允许打破** | ⚠️ **必须重做插件**（`base_version` 变化） | 允许改接缝签名，**须逐项注 `breaking`** |
| **MINOR**（第二位） | 功能版本（阶段级交付，如 `1.6.0 → 1.7.0`） | ✅ **不受影响** | 契约**只加不改**；接缝签名不变 |
| **PATCH**（第三位） | **补丁**（线上缺陷修复） | ✅ **不受影响** | **契约零 diff + 接缝签名快照逐字相同**（G-11） |

### 7.2 `base_version` 定义（**消歧**）

**`base_version` = MAJOR 段**（当前 = `1`）。

- `1.6.0 → 1.7.0 → 1.8.0`：**`base_version` 恒为 `1`** ⇒ 插件**无需重做**
- `1.x → 2.0.0`：**`base_version` 由 `1` 变 `2`** ⇒ 插件需重新开发（**即 ADR-0007 的商业承诺**）

> **⚠️ 与 ADR-0007 表述的差异（澄清，非改承诺）**：ADR-0007 §3.8 写作「补丁 = 版本号第三位 `v1.0.x`」，其中 `v1.0.x` 是**举例**，易被读成"版本须为 `1.0.x`"。
> **实际含义是"第三位递增"**：当前 `1.6.0` 的补丁是 **`1.6.1`**，不是 `1.0.x`。**承诺本身不变**，本处仅为消歧——不消歧则 G-11 无从比对。

### 7.3 由此推出的两条硬规则

1. **G-11 快照比对只在 PATCH / MINOR 触发**：MAJOR 递增时允许快照变化，但须在 release notes 列出**全部** `breaking` 项。
2. **`v2.0.0` 是 MAJOR 递增** ⇒ 届时插件需重新开发 ⇒ **该事实须写进首份商业合同**，避免"免费重做"的预期落差。
