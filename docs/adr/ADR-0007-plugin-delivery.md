## 1. 背景（Context）

本项目是**源码二开 + 私有化交付**的产品，客户买到的是一套部署在自己环境的系统，且**每个客户都有自己的定制**（对接其 LDAP / OA / 对象存储 / 特殊业务功能）。

由此产生四个必须回答的问题：

1. **"乐高"发生在哪里**——客户定制能否像"放一个插件就多一个功能、撤走就恢复"？
2. **升级补丁粒度**——客户报了 bug，能不能像传统企业软件那样"出一个补丁包"就地解决，而不必整包重发？
3. **语言栈**——"换一个 JAR"这件事是不是 Java 才有，Python 做不到？要不要换 Java？
4. **N 个客户的维护成本**——若每个客户一份定制代码，公司成本是否失控？

**失败代价不对称**：定制若侵蚀基座，三年后会出现 20 份实现同一件事的业务代码，届时**任何一次基座升级都要回归 20 遍**——这是能拖垮交付团队的慢性病；而插件边界画错，早期几乎无感。

---

## 2. 决策（Decision）

**八条裁决，构成一个自洽的交付模型：**

| # | 裁决 |
|---|---|
| **1** | **插件在构建期烘焙（build-time composition），不在客户现场运行时热插拔** |
| **2** | **部署单元 = 一个租户**：一套 `docker-compose` = 一个租户 |
| **3** | **单一代码库 + variant 配置**：镜像有 N 份，**代码永远只有 1 份** |
| **4** | **定制分三档 L0 / L1 / L2**，默认把 90% 的定制逼到 L0 / L1 |
| **5** | **插件分 A / B 两类**：A 类纯配置（零前端改动），B 类自带契约片段与前端 |
| **6** | **坚持 Python，不换 Java** |
| **7** | **补丁 = 新 tag 镜像 + registry 分层拉取**，补丁位（第三位）受三条纪律约束 |
| **8** | **v1.x 内八个接缝的接口签名冻结**（用户裁决：付费升 V2.0 才允许插件失效、需重新开发） |

## 3. 实现要求（Mandatory）

### 3.1 为什么"乐高"在构建期而非运行时（裁决 1）

三条约束叠起来是硬性的，决定了运行时热插拔**不可行**：

| 约束 | 出处 |
|---|---|
| 禁客户现场编译 | `deployment-spec.md` §1.2 |
| 依赖必须 baked 进镜像、禁现场 `pip install` | `deployment-spec.md` §4 注 |
| 数据不出内网 | PRD H6 |

⇒ 客户拿到的必然是**一个烘焙好的完整镜像**。

**"乐高"因此发生在我们这边**，不在客户现场：

| 环节 | 谁做 | 做什么 |
|---|---|---|
| 选积木 | 实施同学 | 写一份 `deploy/variants/<客户>.yaml`，声明启用哪些插件与配置 |
| 拼装 | **构建机**（完全离线，与客户环境无关） | Docker 构建时把插件 COPY 进镜像 |
| 交付 | 客户侧 | `docker load` 或 `docker pull` + `compose up -d` |
| 撤积木 | 同上 | 改 variant 列表，重新出镜像，换回去 |

**这个形态更符合商业逻辑**：客户现场永远是一个黑盒镜像，**没有运行时热插拔，也就没有状态漂移**；且"基座能单独交付"天然成立——不填 variant 即纯净基座镜像。

### 3.2 variant 清单（裁决 3 的载体）

```yaml
# deploy/variants/<customer>.yaml
customer: customerA
base_ref: v1.0.2                 # 基座版本（含补丁位）
plugins:
  - id: ldap-auth                # 对应 ADR-0004 接缝 1
    version: 1.2.0
    config: { ldap_url: "...", base_dn: "..." }   # A 类插件的配置值
  - id: oa-webhook               # 接缝 5
    version: 0.9.0
domain_profile: attendance       # 业务域 profile（本体、语料、终端类型优先级）
```

**纪律**：

- **基座代码与插件代码同处一个仓库**（单一代码库）；variant 文件只描述"启用什么"，**不含业务代码**。
- 每新增一个客户 = 新增一份 variant 文件，**不新增一份代码分支**。
- 禁止出现"客户分支"（`feature/customerA`）——那是本 ADR 要消灭的对象。

### 3.3 部署单元 = 一个租户（裁决 2）

- 默认隔离走**方案 A**：一套部署 + `org_id` + RLS（见 `ADR-0003` §3.7 裁决二）。
- 但**部署单元按"一套 compose = 一个租户"设计** ⇒ 客户要求子公司**物理隔离**时，只需**多起几套**，**不改代码**。
- 镜像 tag 规范：`<base_version>-<variant>`，如 `v1.0.2-customerA`。

### 3.4 定制三档（裁决 4）——成本控制的主杠杆

| 档 | 内容 | 例子 | 维护成本 | 策略 |
|---|---|---|---|---|
| **L0 配置** | 零代码，改值即可 | 客户名、域账号、阈值、开关、考勤规则、审批流 | **≈ 0** | **尽量往这里推** |
| **L1 适配器** | 对接客户系统的适配代码 | LDAP（接缝 1）、OA webhook（接缝 5）、对象存储（接缝 2） | 低（接口冻结则不用动） | 对应 ADR-0004 八个接缝 |
| **L2 业务定制** | 客户专属业务逻辑 | 定制报表、专属审批流 | **高——成本黑洞** | 尽量不做；做则**单独报价 + 单独维护合同** |

**核心手段**：把业务规则（考勤规则、审批流、报表字段）做成**配置项 / DSL / 数据库里的规则**，而不是写进代码。一旦做成配置，它随基座自动升级，**永不产生维护成本**。

### 3.5 插件两类（裁决 5）

| 类型 | 典型例子 | 契约方案 | 前端改动 |
|---|---|---|---|
| **A 类｜纯配置** | LDAP 地址、对象存储 AK/SK、OA webhook、业务阈值 | **不碰契约** | **零**——manifest 声明配置项，基座通用设置页**动态渲染表单** |
| **B 类｜要新页面 / 新端点** | 定制报表、专属审批流 | 插件自带 `openapi.<id>.yaml` 片段 | 插件自带前端页面（**构建期并入**） |

**判据**：默认一律做 A 类；**确证"配置项搞不定"才升 B 类**，并在 variant 里显式登记升级理由。

> 八个接缝中**绝大多数是 A 类**（地址 / 凭证 / 输出目标）⇒ 多数客户项目可做到**零前端改动、只配不看代码**。这才是可复制的项目型交付。

### 3.6 插件 manifest 与契约分片

```yaml
# plugins/<id>/plugin.yaml
id: ldap-auth
version: 1.2.0
base_version: "1"          # 兼容基座**大版本**；跨大版本需重做（裁决 8）
class: A                   # A = 纯配置 / B = 带 UI 与新端点
seam: 1                    # 对应 ADR-0004 接缝编号
entry_point: app.services.auth.ldap:LdapAuthProvider
config_schema: { ... }     # A 类：驱动基座动态表单
openapi_fragment: null     # B 类才填 contracts/plugins/<id>.yaml
```

**契约纪律（与"预留字段不进契约"同源）**：

```
contracts/openapi.yaml              ← 基座（纯净，永不污染）
contracts/plugins/<id>.yaml         ← B 类插件自带片段
构建： scripts/build_contract.py --variant <customer> → build/openapi.<customer>.yaml
校验：每个片段单独过 export_openapi.py --check（片段自身与实现一致）
生成： npm run gen:api（读 build/ 那份）⇒ 前端类型含该客户插件
```

**插件不得写进基座 `openapi.yaml`**；但**每个变体可以有自己的合并后契约**，构建期拼出。

### 3.7 语言栈：坚持 Python（裁决 6）

**结论：不换 Java。** 三条理由，第三条是决定性的。

1. **"JAR 能打进去"不是 Java 的语言能力，是部署形态的产物**。换 JAR **通常也要重启**（Tomcat `lib/`、Spring Boot fat jar）；真正不重启的只有 OSGi，而 OSGi 在企业应用中**已基本消亡**。在"换模块 + 重启"这一维度，Python 的 `pip install -U` 与之**等价**。
2. **容器化部署下 Java 与 Python 完全等价**——都得重建镜像。
3. **本项目是 LLM / GraphRAG 项目**：`backend/pyproject.toml` 的核心依赖为 `langchain-openai` + `neo4j`。**Python 是 LLM/RAG 生态的第一语言，且是断层式领先**；Java 侧的 LangChain4j 生态成熟度差一个数量级。

⇒ 换 Java 的账单：后端**全量重写** + 团队技能栈切换 + 现有全部测试 / 契约门禁 / openapi 体系作废 + 未来每个 LLM 新特性自行实现。**用 100% 的成本买 0% 的收益。**

> 若将来听到"Java 才能做插件"，那是把**部署形态问题**误诊成了**语言问题**。

### 3.8 补丁粒度与三条纪律（裁决 7）

#### 3.8.1 补丁怎么走

客户机**通常有外网**（用户 2026-10-01 澄清：客户购买云主机部署）⇒ 采用 **registry 模式**：

```
你：修 bug → 打 tag v1.0.2 → CI 推镜像（含各 variant）
客户：docker compose pull && docker compose up -d
```

`backend/Dockerfile` **已做依赖先行分层**（第 23–27 行）⇒ `docker pull` **只传变化的那一层**（通常几 MB），体感接近"丢一个 JAR"。

> ⚠️ `deployment-spec.md` §1.1 原文写"客户机无外网，不能 `docker pull`"，**与事实不符**，须修订为**双模式**：云主机客户走 registry（默认），真内网集团客户走离线 tar（保留）。

#### 3.8.2 为什么镜像版本化优于"文件级补丁"

| | 换 JAR / 覆盖文件 | 换镜像 tag |
|---|---|---|
| 原子性 | 手工换文件，可能半新半旧 | 整个镜像一个版本，原子的 |
| 回滚 | 得记得上一个版本是哪个 | 改 tag 回去 |
| 现场状态 | **会漂移**——半年后无人知道现场跑的是什么 | digest 唯一，永远可查 |
| 可复现 | 依赖环境里其他组件 | 完全自包含 |

⇒ **不要羡慕 JAR。镜像版本化严格优于文件级补丁。**

#### 3.8.3 补丁三条纪律（版本号第三位 `v1.0.x`）

| # | 纪律 | 违反后果 | 机器判据 |
|---|---|---|---|
| **1** | **不改 `contracts/openapi.yaml`** | 前端 artifact 与后端错版 | 已有 `export_openapi.py --check`；PR 出现 diff 即红 |
| **2** | **不改八个接缝的接口签名** | 客户已装的插件在补丁后**偷偷失效** | **新增：接缝签名快照测试**（§3.9） |
| **3** | **数据库只允许向后兼容的加法** | 补丁后旧库缺列，运行时才炸 | Alembic 迁移 + 升级演练（`deployment-spec.md` §7） |

**补丁定义**：只修 bug，**不得**改契约、**不得**改接缝签名、**不得**改插件接口、**不得**做破坏性 schema 变更。需破坏性变更 ⇒ 升**大版本**。

### 3.9 接缝签名冻结（裁决 8 的落地）

**用户裁决**：付费升 **V2.0** 时插件失效、需重新开发 ⇒ 同一大版本内，插件**不得因打补丁而失效**。

这句话此前**没有任何东西保证它成立**——补丁改一行 `AuthProvider.authenticate()` 的参数，客户的 LDAP 适配就废了，且是补丁后的某次登录才炸。

⇒ 增加**签名快照测试**（与 `check_seams.py` 同族）：

```
提取八个接缝的公开接口签名（module.Class.method → 参数名 / 默认值 / 注解）
→ 存 JSON 快照 → 变了即 CI 红
```

**规则（一句话）**：

> **打 `v1.x` 补丁 ⇒ 快照必须逐字相同；只有 bump 大版本才允许改快照**，且该次提交必须显式注明 `breaking`。

这把商业决策变成了 CI 里不可绕过的判据：**V2 才会让插件失效，且有意为之，不是意外。**

## 4. 后果（Consequences）

### 正面

- ✅ **成本从 O(N) 代码降到 O(1) 代码 + O(N) 机器**：改基座一处，CI 遍历 variant 自动重建。
- ✅ **客户现场无状态漂移**：永远是完整镜像，排障时"现场跑的是什么"可秒答。
- ✅ **可回滚**：改 tag 即可，无需记住上一个补丁文件。
- ✅ **定制成本可见**：L0 ≈ 0、L1 低、L2 高 ⇒ L2 自然触发单独报价。

### 负面（已知并接受）

- ⚠️ **构建矩阵增长**：N 个客户 = N 份构建产物，必须用 `deploy/variants/*.yaml` 显式声明 + 一条命令构建，否则半年后无人知道客户 B 的镜像里烘焙了什么。
- ⚠️ **O(N) 的回归验证不可避免**：基座改动 ⇒ 每个 variant 都要跑「基座冒烟 + 该变体插件自检」，**必须 CI 化**，否则人工回归会先崩。
- ⚠️ **不支持运行时热插拔**：客户不能自己加插件——这是既定取舍（换取零状态漂移），须在售前讲清。
- ⚠️ **补丁包体积**：离线 tar 模式下客户需拉全量镜像；registry 模式下只传变化层。⇒ 云主机客户优先引导 registry。

## 5. 备选方案与取舍

| 方案 | 拒绝理由 |
|---|---|
| **运行时热插拔插件**（客户现场装） | 违反 `deployment-spec.md` §1.2 禁现场编译 / 禁 `pip install`；且引入状态漂移与"现场到底是什么"的排障黑洞。 |
| **每个客户一个代码分支** | 正是本 ADR 要消灭的对象：基座升级要回归 N 遍，三年后 20 份重复业务代码。 |
| **换成 Java 以求 JAR 式补丁** | 见 §3.7：容器化下与 Python 等价；且本项目为 LLM/RAG，Python 生态无可替代。**用 100% 成本买 0% 收益。** |
| **全部定制都做成插件（不分层）** | L2 业务定制做成插件后仍需随基座演进，成本照旧；分层才能把多数定制压到 L0。 |
| **插件字段写进基座 `openapi.yaml`** | 基座契约变成"所有客户功能的并集"，交付 B 客户时带着 A 客户的 LDAP 字段 ⇒ **污染**，且违背"基座是通用产品"。 |
| **为每个客户维护独立数据库 schema** | 见 `ADR-0003` §5：不作为默认；物理隔离需求由"一套 compose = 一个租户"覆盖。 |
