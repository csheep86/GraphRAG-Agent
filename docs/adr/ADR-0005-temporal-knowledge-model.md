# ADR-0005 · 知识图谱时效模型：自研双时态 + 确定性仲裁

> **文档编号**：ADR-0005
> **版本**：v1.0
> **状态**：**Accepted**（2026-09-27，架构师；依据 = 双轨 PoC 实测，见 §3）
> **决策者**：架构师（用户 2026-09-27 认可"用实测证据定路线，不做保守选择"）
> **关联**：`docs/optimization-plan-2026-09.md` §3 P3、`specs/m2-extract-kg.md` §3 验收 8–10、`docs/acceptance-traceability-matrix.md` §3.5、`temporal_poc/README.md`

---

## 1. 背景与问题

图谱当前是**纯静态**的：三元组无时间属性，同一属性在不同日期的两份披露文件里
（如法定代表人 张三 → 李四）会以**两条边静默共存**，问答无法区分"当前有效"与"已过期"。

证据（2026-09-27 复核）：

- `backend/` 全文搜索 `valid_from|valid_to|as_of_date|document_date|temporal` = **0 命中**；
- `db/models.py` 的 `Document` **无发布日期字段**；
- `import_to_neo4j.py` 写入以 `(id, kg_version)` 为幂等键 ⇒ 矛盾事实按版本并存，不判定失效。

该债项目自身早已登记（`docs/v1.1.0-demo-mvp-plan.md:399`、
`docs/adr/0004-integration-seams.md:135`：图谱时效边 `valid_from` / `valid_to` 登记 v1.5+，**未设计与实现**）。

**要回答的决策问题**：这个功能，是引入开源时态图谱框架，还是在自研主干上实现？

---

## 2. 决策

> **D-1（主线）**：**保留自研主干，按双时态模型自建时效能力；不引入 Graphiti 作为运行时依赖。**
> **D-2（数据模型）**：边的时效采用**四字段双时态模型**（事实维 + 摄入维）+ 血缘，字段命名沿用本项目口径。
> **D-3（仲裁）**：事实失效判定走**确定性规则**，不依赖 LLM 判断矛盾。
> **D-4（备选保留）**：Graphiti 保留为**备选方案**，再审条件见 §7。

一句话理由：**你的差异化在"上层业务语义"，痛点在"底层时态机制"——这两件事可解耦。
实测表明：自研侧用确定性规则即可达到 3/3，而引入 Graphiti 在当前模型条件下只有 0/3～1/3，
还要额外背上 Embedding 与结构化输出降级的负担。**

## 3. 决策依据：双轨 PoC 实测（**不是读文档得出的**）

> 完整实验记录、可复现脚本与踩坑清单见 **[`temporal_poc/README.md`](../../temporal_poc/README.md)**。
> 本 ADR 只摘录结论，避免成为第二真源。

**实验设计**：同一份语料（同一公司两期文本，法定代表人 / 注册资本 / 住所三类易过期事实）、
同一组判分口径、重复 **3 轮**（单次成功只能证明"能跑"，重复才能证明"敢进生产"）。

| 指标 | Track S（自研） | Track G（Graphiti） |
|---|---|---|
| 时态字段抽取 | ✅ `valid_from` 覆盖率 **100%**（DeepSeek 稳定产出） | ✅ `valid_at/invalid_at` + `created_at/expired_at` 齐全 |
| **当前值正确** | ✅ **3/3** | — |
| **as-of 回溯正确**（2024-06-01 → 张三） | ✅ **3/3** | — |
| **过期治理（旧事实自动失效）** | ✅ **3/3**（确定性规则） | ❌ **1/3**（占位向量）→ **0/3**（真实语义向量） |
| 历史保留 | ✅ 3/3（失效边保留可查） | ✅ 保留（`expired_at` 标记） |
| 单轮耗时 / LLM 调用 | ≈ 8.5s / **2 次** | ≈ 10–11s / **多次**（抽取 + 去重 + 矛盾判定） |
| 新增依赖 | **0**（复用现有 DeepSeek 通道） | graphiti-core + **必须补 Embedding** + cross-encoder |

**关键对照实验（证伪干扰项）**：一开始只有占位哈希向量，可能压低 Graphiti 表现。
装上真实中文语义模型 `bge-small-zh-v1.5` 重跑 ⇒ **1/3 → 0/3**，没有变好。
⇒ 失败**不是** Embedding 造成的，是它在当前条件下本身的表现。

**根因（本次最有价值的发现）**：Graphiti 把**变更陈述句本身**单独建成一条边并判它失效，
而**真正该过期的旧边依然存活**：

| 边的 fact | invalid_at | 结果 |
|---|---|---|
| …法定代表人**由张三变更为李四** | 2025-05-01 | 失效 ← 错杀了陈述边 |
| **…法定代表人为张三** | **None** | ❌ 该过期的反而活着 |
| 自 2025 年 5 月起…变更为李四 | None | ✅ 存活 |

即"张三"与"李四"**同时是当前事实**——正是我们要消灭的病态。

**为什么自研反而不犯这个错**：本项目有**受控 schema**（`relation_type` 是枚举）。
同一 `(head, relation_type)` 出现不同 `tail` 就是**结构性矛盾**，精确匹配即可判定；
Graphiti 是**开放抽取**，事实写作是自由文本（"为张三" vs "变更为李四"），
只能靠语义相似度 + LLM 比较自然语言，噪声大得多。

## 4. 数据模型（D-2）：四字段双时态

抄 Graphiti 的模型（这是它**最值钱**的部分，比它的自动仲裁更值得抄），
字段命名沿用本项目已有口径（`valid_from` / `valid_to`，见 `optimization-plan-2026-09.md` §3 P3）。

| 本项目字段 | Graphiti 对应 | 维度 | 含义 | 空值语义 |
|---|---|---|---|---|
| `valid_from` | `valid_at` | **事实维** | 事实开始成立的日期 | 不可空；文本无显式日期时**取 `document_date`**（不猜） |
| `valid_to` | `invalid_at` | **事实维** | 事实失效日期 | **NULL = 仍有效** |
| `created_at` | `created_at` | **摄入维** | 本条边写入图谱的时间 | 不可空 |
| `expired_at` | `expired_at` | **摄入维** | 本条边被取代（不再当前）的时间 | NULL = 仍是当前边 |
| `source_document_id` | `episodes` | **血缘** | 该事实来自哪份文档 | 不可空 |

**两套维度的区分（必须，否则会做成"半时态"）**：

- **事实维**回答"这件事在现实中从什么时候到什么时候成立"——来自**文档**；
- **摄入维**回答"我们什么时候知道、什么时候被推翻"——来自**系统**。

只有事实维 ⇒ 无法解释"同一份文件重跑，旧边去哪了"；
只有摄入维 ⇒ 无法回答"2024 年中的法定代表人是谁"。

**与 `kg_version` 的正交关系（澄清，避免混淆）**：

| 概念 | 回答什么 | 粒度 |
|---|---|---|
| `kg_version` | 图谱**快照**的哪一次构建（可回滚、可比对） | 全图一次构建 |
| 四字段双时态 | 单条**事实**的成立区间（可回溯、可失效） | 单条边 |

二者**正交**：一个 `kg_version` 内可以有多条不同 `valid_from` 的边；
同一条事实（同一 `valid_from`）也可能在多个 `kg_version` 中被重建。**不得互相替代。**

## 5. 仲裁规则（D-3）：确定性，不依赖 LLM

> 规则输入只需要 `(head, relation_type)` + 时间，**不需要 Embedding，不需要 LLM 调用**。
> 这正是受控 schema 相对开放抽取的结构性优势。

### R1 跨文档（不同 `document_date`）

同一 `(head, relation_type)` 出现新事实，且其 `valid_from` **严格晚于**已有边的 `valid_from`：

```
旧边.valid_to   := 新边.valid_from
旧边.expired_at := 写入时刻
```

### R2 同文档内变更句（同锚点）

「自 2025 年 5 月起，法定代表人由张三变更为李四」这类句子会**同时**抽出旧值与新值，
且两者 `valid_from` **相同** ⇒ R1 管不到。规则：

```
同 (head, relation_type) 且 valid_from 相同的多条边
  → 保留 tail 在原文中【最晚出现】的那条（变更目标值）
  → 其余 valid_to := valid_from（立即失效）
```

### R3 禁止同批次互封

失效动作**不得**作用于同一批次（同一 episode / 同一文档）内刚写入的边。

> **这条是实测踩出来的**：首版实现用 `valid_from <= 新值` 且不排除同 episode，
> 导致变更句先写出"李四边"、后写出的"张三边"**反过来把李四边封掉**，
> 当前值全线阵亡（见 `temporal_poc/README.md` §4 坑 5）。R1 的"严格晚于"与 R3 共同防此。

### R4 不猜值纪律

文本未显式给出起止日期时，`valid_from` **取 `document_date`**，
`valid_to` **留 NULL**——**不得**由模型或代码推断区间。

### R4-b 文档级作用域继承（Sprint 10.5 增补，用户 2026-09-30 裁决）

条款（`<entity>` 上挂不得的东西，此处指作为桥接边尾端的 `POLICY_CLAUSE`）
**自身一个候选窗口都没有**时，允许继承**其所属文档**显式声明的窗口：

```
文档窗口 := 该文档自称条款（含 本规定 / 本制度 / 本办法 / 本细则 之一的行）里
            逐字写出的 (施行日, 有效期至)
施行日   := document_date          ← 与 R4 同源，R4 本就允许
有效期至 := 仅在正文逐字写出时取该值；没写 ⇒ NULL（不推断）
```

硬边界（四条，逐条都可能被误用）：

1. **只在自身无窗口时填补**，已有窗口绝不覆盖；
2. **歧义 ⇒ 留空**：同一条款出现在窗口不同的多个文档中 ⇒ 留 `None`；
3. **来源必须是文本**：严禁按文件名 / 路径 / 标题里的年份推定——M5 §4.5 只落
   `filename_hash`，**本来就没有文件名可依据**；
4. **不许用任何其他方式造 `valid_to`**：既不许把施行日同时当成失效日，也不许套
   「当年 12-31」这类常识补值。

> 为什么必须允许 `valid_to` 一侧：2025 版语料若在 `valid_to` 上留 `NULL`，
> 语义就是「2025 版仍有效」——as-of 双时点会变成「两个时点都回答现行条款」，
> 与「不给日期」同样假，却**更难被发现**。此为 R4 措辞边界的增补，**不是放松 R4**。
>
> 完整实测与验收基线见
> [`changes/P6-U/12-document-scope-inheritance.md`](../../changes/P6-U/12-document-scope-inheritance.md)。

### R5 as-of 视图的证据位次（Sprint 10.5 增补，用户 2026-09-30 裁决）

给定时点提问时，**同一问句可能有多条候选链在全部语义维度上打平**。此时必须有一条
口径决定谁胜出，否则答案由实现细节（字典序）决定——那不是"选了一条"，是"随便一条"。

```
证据位次（仅在 as_of 非 NULL 时启用）:=
    0  该链**最后一跳**被该时点证实：
       valid_from <= as_of 且 (valid_to IS NULL 或 valid_to > as_of)
    1  最后一跳**没有任何日期** ⇒ 不可判定 ⇒ 让位
       （**保留候选资格，不剔除**）
as_of 为 NULL ⇒ 该维度恒为 0 ⇒ 缺省视图零变化（硬要求）
```

三条硬边界：

1. **位置在字典序之前、在跳数与终点类型之后** ⇒ 只为"打平的候选"裁决，**绝不**
   为了时点证据去挑一条更短或更有解释力的链；
2. **让位 ≠ 剔除**：只有无日期候选时仍照旧选中——R4「不知道就说不知道」在此处的
   含义是"不把未知说成已证实"，**不是**"把未知删掉"；
3. **只在最后一跳上判定**：终点是答案的落点，把一个在该时点根本不成立的条款摆在
   用户面前，比"中间某跳有没有日期"更致命。

> 为什么要补这一维（实测，**不是推测**）：`李静的缺卡该怎么处理？` 在
> `as_of='2025-06-01'` 下的 12 条候选，其终点类型优先标志、`_TERMINAL_RANK`、跳数、
> 时序裁决四项**全部相同**，胜出者纯由 `ids` 字典序决定 ⇒ 答案事实上随机。
> 诊断记录见
> [`changes/P6-U/probe_as_of_ranking.py`](../../changes/P6-U/probe_as_of_ranking.py)。

## 7. 后果与被否方案

### 7.1 接受的正面后果

1. **零新增运行时依赖**：复用现有 DeepSeek 通道，不引入 graphiti-core / Embedding 服务；
2. **确定性可预测**：仲裁是规则，出错可定位（实测首版 bug 一次定位一次修掉）；
3. **schema 优势兑现**：`(head, relation_type)` 精确匹配比语义召回更准、更省（2 次 LLM vs 多次）；
4. **可平替**：字段模型与 Graphiti 一致，日后若换引擎是"平替"不是"重写"。

### 7.2 接受的负面后果（不隐瞒）

1. **增量更新能力需自建**：Graphiti 自带的增量 episode 摄入与去重，自研侧要自己写（L1 范围）；
2. **语义级矛盾识别弱于 LLM 方案**：跨 `relation_type` 的隐含矛盾（如"注册地迁走"与"办公地址新增"）规则抓不到 ⇒ 接受，L2 只覆盖路径时序一致性；
3. **有效期策略需人工配置**：不同 `relation_type` 的有效期（如任职 vs 注册地址）按枚举配置，属"工程版 Relation-aware Decay，零训练"（见 `optimization-plan-2026-09.md` §3 P3-L1）。

### 7.3 被否方案与理由

| 方案 | 否定理由 |
|---|---|
| **引入 Graphiti 全量接管** | 过期治理实测 **0/3**；需 DeepSeek 降级到 `json_object`（实测默认 `json_schema` 直接 400，`response_format type is unavailable`）；需额外补 Embedding 与 cross-encoder；会失去对 `ExtractedRelation` schema 的控制 |
| **引入 Graphiti 只做时态引擎层** | 同样受制于它的矛盾判定（0/3）；且其候选召回依赖语义相似度，与本项目受控 schema 的精确匹配相比是劣势 |
| **换 WeKnora / Yuxi / qKnow 成品平台** | 技术栈不同（Go / Java / Milvus）⇒ 现有 backend 11,750 行 + frontend 9,945 行**全部报废**；且**它们同样不解决知识过期**（静态图谱） |
| **KnowLion** | 高度绑定商业图库 AbutionGraph，非主流、社区极小 |
| **ATOM / iText2KG** | 五元组抽取思路值得借鉴（已吸收进 v3 prompt 的 `valid_from` / `valid_to`），但冲突仲裁仍需自写 ⇒ 以"借设计"而非"引依赖"的方式采纳 |

### 7.4 再审条件（Graphiti 何时重新进入评估）

同时满足以下三条时，重跑 `temporal_poc/repeat_g.py`（n ≥ 3）：

1. 本项目已引入**真实中文语义 Embedding**（届时是既有能力，不再是额外成本）；
2. 供应商模型**原生支持 `json_schema` 结构化输出**（不再走 `json_object` 降级）；
3. 命中率 **≥ 2/3**。

达到 ⇒ 可把图谱引擎层换成 Graphiti（因字段模型一致，属**平替**）；未达到 ⇒ 维持本 ADR。
