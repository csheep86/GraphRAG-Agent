### 0.2 核心结论摘要（TL;DR）

1. **需求侧：痛点真实存在，但价值高度集中在少数场景。** 16 条候选痛点中只有 5 条加权得分 ≥ 4.25，且**这 5 条全部满足"痛感强度 = 5 且现有替代方案缺陷度 ≥ 4"**——即"很痛"且"现有工具真的解决不了"同时成立。
2. **真正的分水岭不是"多模态"，而是"图谱是否必需"。** **只有 P1（投研股权/供应链穿透）、P3（财务关联交易识别）、P5（运维变更影响面）属于"图谱必需"**，因为答案形态是**路径**或**集合**，纯向量检索原理上无法表达；**P2（法务条款一致性）、P4（合规义务映射）用普通 RAG + 结构化抽取即可覆盖大部分价值**，图谱只是边际增强。
3. **竞品未解决不是因为"能力差一点"，而是"解空间不重叠"。** 通用对话工具（ChatPDF / Notion AI / Copilot / Glean）的检索机制是**向量相似度**，**"相似 ≠ 可达"，多跳关系在其范式下结构性无解**；图谱型与开源方案能表达关系，但以**库**的形态存在，把解析、本体、治理、成本全部留给客户自建。
4. **市场空白位于"产品型"与"开源型"之间：私域可部署 + 本体可逐步校正 + 答案可溯源到实体与原文 + 成本可控的一体化交付。** 能力矩阵中**没有任何一列同时满足「多模态解析 ✅ + 图谱多跳 ✅ + 私域 ✅ + 治理 ⚠️/✅」**。
5. **总体判定：条件性 GO（评分 3.45 / 5）。** **推荐首个验证靶点为 P3（财务关联交易识别）**——CSV 结构化输入、gold 关系可人工植入、指标客观，**最快能被证伪**；建议以"**单场景、≤ 6 周、≤ 3 人**"的最小验证替代全量立项，并设置三条硬性反证条件（见 3.4）。

### 1.4 Top 5 痛点详解

> 每条痛点按 ① 场景 ② 现状 ③ 为什么失效（标注根因类型）④ 本方案对应能力 ⑤ 可验证的最小实验。

#### P1（对应 C7）投研 / 行研：招股书 · 年报 · 研报中的股权与供应链穿透

**① 场景描述（谁 · 流程 · 卡点）**
买方 / 卖方研究分析师，在尽调或行业覆盖流程中，需要回答"标的公司 A 的实际控制人是谁""A 的关键供应商中哪些同时向竞争对手 B 供货"。**卡点动作**：从数十至数百份 PDF（招股书、年报、公告、研报）中人工摘出股权层级与供应商名单，再手工拼接成"人 → 公司 → 供应商"链条。

**② 现状如何解决**
Excel 手工台账 + PDF 关键词检索 + 商业数据终端（Wind / Choice 类，**E1 待复核**）+ 人工撰写纪要。

**③ 为什么失效（根因）**
**根因类型：数据源问题 + 工具能力不足（E3，置信度 高）。** 关联方与供应商信息分散在股权结构图、表格、脚注、附注中；同一实体在不同文件中指称不同（全称 / 简称 / 曾用名 / 英文名），**关键词检索无法跨文件消解同一实体**；商业终端 schema 固定、覆盖面有限，对非上市主体与海外实体常不覆盖。**人工拼接在 3 层以上股权穿透时极易断链。**

**④ 本方案对应的能力**
MinerU 结构化解析 PDF 表格与章节 → LangExtract 抽取实体（公司 / 自然人 / 机构）与关系（持股 / 子公司 / 供应商 / 实控人）→ **实体消解（归一化）** → KG 多跳遍历 → GraphRAG 生成**带原文引用的**答案。对应 `prompts/entity_relation_extract_v1.md`（实体 / 关系 + evidence + confidence）与 `prompts/kg_qa_v1.md`（每条结论附 `[source: ...]`）。

**⑤ 可验证的最小实验**
- **样本量**：50 份公开披露文件（30 招股书 + 10 年报 + 10 研报）。
- **标注**：人工标注 200 条 gold 关系（含 ≥ 60 条需 2 跳以上的）。
- **通过指标**：① 关系抽取 precision ≥ 0.85；② 3 跳内多跳问题端到端答对率 ≥ 0.80；③ **答案引用可回溯到原文 span 的覆盖率 = 100%**。
- **通过线**：precision ≥ 0.85 **且** 引用覆盖率 100%。**引用覆盖率不达标即判失败**——投研场景对可溯源性零容忍。

#### P2（对应 C1）法务：主协议 + 附件 + 补充协议的条款一致性核对

**① 场景描述**
企业法务 / 合同管理岗，在交易谈判或签署前的审查流程中，需核对"主合同第 8 条违约责任"与"补充协议第 3 条"是否冲突、定义条款是否被前后一致引用、金额 / 期限 / 管辖条款是否在版本间漂移。**卡点动作**：逐条人工比对多个版本。

**② 现状如何解决**
Word 比较文档 / 版本对比 + 人工逐条阅读 + 部分企业部署 CLM（合同生命周期管理）系统。

**③ 为什么失效（根因）**
**根因类型：工具能力不足为主 + 组织流程问题为辅（E3，置信度 高）。** Word diff 只能做**字符级差异**，无法判断"换了表述但语义相同 / 相反"；CLM 系统多为**元数据 + 全文检索**，不建模"条款 → 被引用 → 定义"的**语义引用链**；条款编号在不同版本重排时纯 diff 会**噪声爆炸**，法务最终仍退回人工。

**④ 本方案对应的能力**
LLM 条款结构化（编号 / 主题 / 引用）+ 跨文档条款对齐 + **定义链的图遍历**（定义条款 → 引用它的条款）+ GraphRAG 输出带引用的差异报告。**注意：本条图谱为"增强"而非"必需"（见 1.5）。**

**⑤ 可验证的最小实验**
- **样本量**：20 份合同 = 3 组"主协议 + 附件 + 补充协议"，其中**人工植入 15 处真实冲突 + 15 处同义改写**。
- **通过指标**：① 冲突召回 ≥ 0.90；② 误报 ≤ 2 处 / 组；③ 同义改写导致的**假冲突率 ≤ 0.20**。
- **通过线**：冲突召回 ≥ 0.90 **且** 假冲突率 ≤ 0.20。**假冲突过多会直接摧毁法务信任。**

#### P3（对应 C12）财务审计：关联交易识别与合同-发票-凭证三方核对

**① 场景描述**
内审 / 外审 / 财务共享中心，在审计底稿编制与关联方披露核查流程中，需判断"这家供应商是否与公司存在**隐性关联**"（同一注册地址 / 同一联系电话 / 同一法人 / 交叉持股）。**卡点动作**：跨合同、发票、记账凭证、供应商台账四类数据做主体对齐与关系推断。

**② 现状如何解决**
抽样人工核对 + Excel VLOOKUP + 部分支持凭证层核对的审计软件。

**③ 为什么失效（根因）**
**根因类型：数据源问题 + 工具能力不足（E3，置信度 高）。** 隐性关联的判定本质是**图上的连通性与环路检测**（A 的股东同时担任 B 的监事 ⇒ 潜在关联），**传统检索与表格公式无法表达这种结构**；同时多源主体名称 / 税号格式不一（供应商主数据 ≠ 合同签章主体 ≠ 发票抬头），**必须做实体消解**才能对齐。

**④ 本方案对应的能力**
多源实体消解 → KG 构建（主体-地址-法人-股东-电话多类节点）→ **图连通分量 / 环路 / 共享邻居查询** → GraphRAG 输出带证据的疑点清单（每条疑点回溯到具体合同 / 发票）。

**⑤ 可验证的最小实验**
- **样本量**：200 份合同（PDF）+ 500 张发票（**CSV 结构化**）+ 100 条记账凭证（CSV），**人工植入 20 组隐性关联**。
- **通过指标**：① 隐性关联召回 ≥ 0.80；② 误报率 ≤ 0.15；③ 三方金额不一致检出率 ≥ 0.95。
- **附加价值**：**该实验恰好验证 CSV 结构化输入通道。**CSV 通道在 P1 / P2 / P4 / P5 中覆盖不足，**必须由 P3 承载**。

#### P4（对应 C2）合规：监管法规义务 → 内部制度 → 控制点的映射与变更影响

**① 场景描述**
合规岗 / 风控，在新规颁布后的差距分析（gap analysis）流程中，需判断"新规（或修订条款）出来后，内部哪些制度 / 流程 / 系统需要修改"。**卡点动作**：一条法规义务往往对应多条内部制度，且制度之间相互引用，人工无法穷举影响面。

**② 现状如何解决**
合规顾问人工梳理 + Excel 合规矩阵（法规条款 × 内部制度映射表）+ 外部律所差距分析报告。

**③ 为什么失效（根因）**
**根因类型：组织流程问题 + 数据源问题（E3，置信度 中高）。** 映射表**靠人工维护、极易过期**；法规修订后**变更无法自动传播**（法规 → 义务 → 制度 → 责任部门的多跳链路）；法规版本多、地方与行业细则交叉，全文检索**命中噪声极大**，而**"漏一条义务"的代价是合规风险**，因此用户不敢信任检索结果。

**④ 本方案对应的能力**
法规与制度的结构化抽取（义务 / 主体 / 动作 / 时限）+ 义务-制度映射图谱 + **变更传播的多跳查询** + GraphRAG 生成差距分析报告。

**⑤ 可验证的最小实验**
- **样本量**：3 部法规（含 1 部带修订版）+ 30 份内部制度。
- **标注**：人工标注 100 条"义务 → 制度"映射。
- **通过指标**：① 映射召回 ≥ 0.80；② **修订后的影响面召回 ≥ 0.85**；③ 误报 ≤ 0.20。
- **通过线**：影响面召回 ≥ 0.85 —— **这是本条相对普通 RAG 的唯一真正差异化指标，若不达标则本条应降级。**

> **风险提示（E4，置信度 中）：P4 是 Top 5 中"图谱必要性"最弱的一条**，可能用"结构化矩阵 + RAG"即可达成 80% 价值。是否保留需靠上述第 ② 项指标裁决。

#### P5（对应 C9）运维 / SRE：配置项与服务依赖的变更影响分析

**① 场景描述**
SRE / 运维 / 发布经理，在变更评审（CAB）或事故根因分析流程中，需评估"改这个中间件版本 / 这条配置，会影响哪些下游服务"，以及"本次故障的根因链条是什么"。**卡点动作**：串接多层依赖，判断影响面。

**② 现状如何解决**
CMDB + 人工评审 + 文档式 runbook + 事故复盘会议纪要。

**③ 为什么失效（根因）**
**根因类型：数据源问题 + 组织流程问题（E3，置信度 高）。** CMDB 数据常**过时、不全**；依赖关系散落在架构图、部署 YAML、runbook、历史工单里，**没有统一的图结构**；**人工串依赖通常只能回溯 1–2 层，更深的传递靠口头记忆**，导致变更事故反复发生。

**④ 本方案对应的能力**
从架构文档 / YAML / runbook（DOCX / PDF / CSV）抽取配置项与依赖 → 构建依赖图谱 → **多跳影响面查询（1 / 2 / 3 层下游）** + GraphRAG 生成变更风险评估。

**⑤ 可验证的最小实验**
- **样本量**：1 套微服务样例（30 个服务）+ 50 份文档（架构说明 / runbook / 变更单 CSV）。
- **标注**：150 条依赖边（人工核对）。
- **通过指标**：① 依赖边召回 ≥ 0.85；② **3 层影响面召回 ≥ 0.80**；③ 答案引用覆盖率 = 100%。
- **通过线**：3 层影响面召回 ≥ 0.80 —— **1–2 层靠人肉也能做，只有 3 层以上才体现图谱价值。**

### 1.5 图谱化必要性判定（GO/NO-GO 的关键分水岭）

> **这是全篇对决策最重要的部分：把"必须图谱化"和"普通 RAG 就够"分清，避免为上图而图。**

**判定标准**

- **图谱必需**：答案形态是**一条路径**或**一个集合**，且必须经过**跨节点遍历 + 跨文档实体消解**才能得到；纯向量检索**原理上无法表达**。
- **RAG 已足够**：核心动作是**对齐、比对、匹配**；结构化抽取 + 向量检索 + LLM 已能覆盖大部分价值，图谱只提供**边际增强**。

| 痛点 | 答案形态 | 是否必须图谱 | 判断依据 |
|---|---|---|---|
| **P1 投研穿透** | 路径（A → 子公司 → 供应商 → 实控人） | **图谱必需** | 需多跳遍历 + 跨文件实体消解，向量检索无法给出路径 |
| **P3 财务关联识别** | 集合 / 环路（隐性关联主体） | **图谱必需** | 本质是图连通性 / 环路检测，检索无法表达结构 |
| **P5 运维影响面** | 集合（N 层下游服务） | **图谱必需** | 依赖传递是多跳可达性问题 |
| **P2 法务条款一致性** | 配对（条款 A ↔ 条款 B 差异） | **RAG 基本够用，图谱为增强** | 核心是"对齐 + 比对"；定义引用链仅带来边际提升 |
| **P4 合规义务映射** | 映射（义务 → 制度） | **RAG 基本够用，图谱为增强** | 本质是 many-to-many 映射，结构化矩阵 + RAG 即可覆盖大部分 |

> **关键结论（E3，置信度 中高）：本方案的"图谱刚需"集中在 P1 / P3 / P5 三条。若研发资源有限，应优先在 P1、P3、P5 中择一验证；P2、P4 建议降级为"RAG-first 版本"实现**，仅当 1.4 中给出的差异化指标（P2 假冲突率、P4 影响面召回）达标后，才追加图谱能力。

**判定逻辑**

1. **先证明图谱有不可替代的价值**：在 P1 / P3 / P5 中选择**数据最易获取、gold 最易标注**的一条。本节倾向 **P3 财务关联识别**，因其含 CSV 结构化输入、gold 可人工植入、指标客观。
2. **再验证"RAG 也能做"的降级假设**：对 P2 / P4 用纯 RAG 基线跑同一套指标。**若 RAG 基线与图谱版差距 < 10%，则该场景判定为"不需要图谱"，应从产品路线图中移除图谱依赖，避免过度设计。**
3. **反向证伪条件**：若 P1 / P3 / P5 中任一条的**多跳答对率 / 影响面召回 < 0.80**，说明当前"抽取 → 图谱 → 检索"链路尚不足以支撑图谱刚需场景，应**暂缓图谱化投入**，退回普通 RAG 版本守住 P2 / P4。

### 1.6 未入选候选的淘汰理由

| 候选 | 淘汰理由 | 根因类型 |
|---|---|---|
| C3 研发文档问答 / C5 客服 FAQ / C15 报销政策问答 / C16 工单相似检索 | **替代方案缺陷度仅 2–3 分**，属"普通 RAG 已成熟"的红海；差异化为零，用户已有可接受替代 | 市场定位问题 |

### 2.4 核心问题：为什么它们没完全解决？（逐条根因）

#### 2.4.1 架构性根因（最根本）

1. **向量检索的"相似 ≠ 可达"**：稠密向量优化的是语义相似度，无法表达 `A 的子公司 → B → B 的供应商 → C` 这类路径。**多跳问题在纯向量范式下结构性无解**（E3，置信度 高）。
2. **分块割裂上下文**：chunk 边界把实体、指代（"其""该公司"）和跨段关系切散，**关系在抽取前就已丢失**（E3，置信度 高）。
3. **缺本体（ontology）/ schema**：产品不定义企业领域实体与关系类型，导致"同名不同物、同物不同名"无法归一，**图谱建不起来或建得脏**（E3，置信度 高）。
4. **名为 Graph，实为"内容 + 权限图"**：Microsoft 365 Copilot 依赖的 Microsoft Graph、Glean 的知识图谱，主要是**文档 / 人员 / 权限的关联图**，不是**实体—关系语义图**，二者不可混为一谈（E3，置信度 中–高）。
5. **长上下文不等于多跳推理**：把全文塞进超长 context 能缓解单点召回，但受 token 成本、lost-in-the-middle、海量语料不可全塞等限制，**无法作为企业级多跳方案**（E3，置信度 高）。

#### 2.4.2 商业定位根因

6. **通用助手不与垂直深水区竞争**：ChatPDF / Notion / Perplexity 追求横向大众覆盖，而图谱需要**领域本体 + 行业 Know-how + 长交付周期**，边际收益与其规模化模型不匹配（E3，置信度 中–高）。
7. **平台厂商自建数据墙**：Copilot 活在 Microsoft 生态、Notion AI 活在自己的工作区。**企业知识跨系统碎片化，而没有任何单一厂商有动力和授权去建"跨墙"图谱**（E3，置信度 中–高）。
8. **搜索厂商用"连接器 + 权限同步"定义护城河**：Glean 的核心竞争力是接数百个 SaaS 源并同步权限，而非深度语义推理——**护城河方向与图谱方向不同**（E3，置信度 中）。
9. **开源框架以"库"定位，不背交付责任**：LLMGraphTransformer / PropertyGraphIndex / neo4j-graphrag 把集成、调优、稳定性交给开发者，**而企业缺工程能力**（E3，置信度 中–高）。

#### 2.4.3 成本根因

10. **全量图谱构建的 token 成本**：GraphRAG 型索引需对**每个 chunk 抽实体关系 + 生成社区摘要**，相对纯向量索引，成本预计**高一个数量级或以上（待核实具体倍数）**（E4，置信度 中）。
11. **增量更新难**：新增 / 修改文档后需重算局部关系与社区摘要，**不像向量可近 O(1) 插入**，运维与成本曲线不友好（E3，置信度 中）。
12. **时延叠加**：多跳图查询 + LLM 合成比单次向量检索慢（**数量级差异待核实**）（E4，置信度 中）。
13. **企业级解析的算力成本**：扫描件 / 复杂表格 OCR（MinerU 类高保真解析）需要 GPU，**成本落在自建侧**（E3，置信度 中）。

#### 2.4.4 数据根因

14. **客户数据质量差**：命名不规范、版本混乱、低质扫描件、无表头表格——**抽取前就"垃圾进"**（E3，置信度 高）。
15. **本体冷启动缺失**：企业没有现成 entity / relation 清单，需与客户共建，属**服务型工作**，难以纯产品化（E3，置信度 中）。
16. **多语言 / 术语 / 缩写归一难**：同一实体多种写法，是抽取准确率的长期拖累项（E3，置信度 中）。
17. **私有数据不可训练 / 评测**：效果难校准，导致厂商**难以承诺 SLA**（E3，置信度 中）。

### 2.5 能力缺口 = 切入空间（真缺口 vs 伪缺口）

#### 2.5.1 真缺口（用户愿意付费 + 现有方案确实补不上）

| # | 真缺口 | 为什么是真缺口 | 置信度 |
|---|---|---|---|
| **GAP-T1** | **私域可部署的"多模态解析 → 图谱 → 多跳问答"一体化交付** | 产品型不可私域 / 无图谱，开源型是割裂的库；企业要的是"能落地的系统"而非"零件" | 中–高 |
| **GAP-T2** | **企业本体（ontology）冷启动与持续维护能力** | 公开产品都不提供，客户又确实没有现成 schema | 中 |

| **GAP-T5** | **成本可控的增量图谱更新** | 直击 GraphRAG 全量重算痛点，是"用得起"的前提 | 中 |

#### 2.5.2 伪缺口（看似没人做 / 做了没人付费）

| # | 伪缺口 | 为什么是伪缺口 | 置信度 |
|---|---|---|---|
| **GAP-F1** | "更强的通用 chat-with-PDF" | 已被 ChatPDF / NotebookLM 低价甚至免费覆盖，用户不额外付费 | 中–高 |
| **GAP-F2** | "全自动从零构建完美企业图谱" | 企业不愿为不确定的自动化买单；愿付费的是**可人工校正的半自动** | 中 |

## 3. 切入建议与 GO/NO-GO 判断

### 3.1 切入建议

#### 3.1.1 推荐切入路径

> **关键结论：不在"通用文档问答"正面开战，而是以「单场景深水区 + 私域可部署 + 全链路可溯源」切入，先在一个"图谱必需"的痛点上做到可量化超越 RAG 基线。**

| 决策项 | 建议 | 依据 |
|---|---|---|
| **首个靶点场景** | **P3 财务关联交易识别与合同-发票-凭证三方核对** | ① 属"图谱必需"（连通性 / 环路检测）；② 唯一能同时覆盖 **CSV 结构化输入**通道；③ gold 可人工植入，**指标最客观、最快可证伪** |
| **第二靶点（备选）** | **P1 投研股权 / 供应链穿透** | 得分最高（4.55）、付费意愿最强，但依赖公开 PDF 表格解析质量（A3 假设待验证），风险高于 P3 |
| **暂不投入** | P2 法务条款一致性，P4 合规义务映射 | **属"RAG 基本够用"**，应先以 RAG-first 版本验证，避免过度设计 |
| **明确不做** | 通用 chat-with-PDF、个人版、通用编辑器 AI（GAP-F1 / F3 / F4） | 属**伪缺口**，正面竞争无胜算 |

#### 3.1.2 差异化能力优先级（按"是否构成不可替代价值"排序）

1. **可溯源到原文 span 的答案引用（覆盖率达 100%）** —— **这是准入条件而非加分项**，投研 / 法务 / 审计三类场景对可溯源性零容忍。
2. **多跳关系查询能力（≥ 3 跳）** —— **这是相对普通 RAG 唯一的结构性差异**，也是 GO/NO-GO 的核心度量对象。
3. **中文复杂表格 / 扫描件高保真解析** —— 决定抽取质量上限（对应 GAP-T4）。
4. **本体半自动冷启动 + 人工校正闭环** —— 对应 GAP-T2，**把"服务型工作"产品化为可复用资产**。
5. **增量图谱更新与成本可控** —— 对应 GAP-T5，决定"能不能用得起"。
6. **权限隔离与审计日志** —— 对应 GAP-T6，**是私域交付的门票**（与项目 `CODEBUDDY.md` 的 trace_id / JSON 日志规范一致）。

#### 3.1.3 反定位清单（明确"我们不是什么"）

- **我们不是**"更强的 ChatPDF"——不做单文档场景的横向功能竞争。
- **我们不是**"通用企业搜索"——不做连接器数量军备竞赛（该方向 Glean 已建立护城河）。
- **我们不是**"图数据库 / 图谱平台售卖"——**交付的是解决业务的系统，图谱是内部机制而非卖点**。
- **我们不是**"全自动零人工图谱"——**接受半自动 + 人工校正**，这是企业真实可接受的形态（GAP-F2）。

### 3.2 GO / NO-GO 评分卡

评分口径：各维度 1–5 分（5 为最优），加权求和后映射判定。

| 维度 | 权重 | 得分 | 加权分 | 评分理由（含证据等级） |
|---|---|---|---|---|
| **需求真实性** | 0.25 | **4.0** | 1.000 | 5 条痛点痛感强度均为 5 且替代缺陷度 ≥ 4；但"付费意愿"尚未经过访谈验证（**E4**），故不给满分 |
| **技术可行性** | 0.25 | **3.0** | 0.750 | 组件齐备（MinerU + LangExtract + 图存储 + LangChain 编排），**但中文抽取 precision 0.85（A4）、表格解析质量（A3）、多跳答对率 0.80 均未实测**（**E4**）；增量更新成本（A5）待验证 |
| **竞争差异化** | 0.20 | **4.0** | 0.800 | 能力矩阵中**无任一竞品同时覆盖"多模态 + 图谱多跳 + 私域 + 治理"**（**E3 领域中高**）；但差异化能否转化为溢价待验证 |
| **单位经济性** | 0.15 | **2.5** | 0.375 | **最大短板**：全量图谱索引 token 成本预计高一个数量级（**E4 待核实**）、增量更新难、解析需 GPU。**成本不达标则整个商业模式不成立** |
| **合规与数据安全风险** | 0.15 | **3.5** | 0.525 | 私域部署天然缓解数据出境风险；但处理合同 / 财务 / 发票属**高敏感数据**，需权限隔离、审计留痕、脱敏，且"日志禁止输出敏感信息"须落实到实现层（**E3 中**） |
| **合计** | 1.00 | — | **3.450 / 5** | — |

**判定映射规则**

| 加权总分 | 判定 |
|---|---|
| ≥ 4.00 | GO：直接立项，进入全量实施 |
| **3.00 – 3.99** | **条件性 GO：仅允许以最小验证投入推进，达标后方可全量立项** |
| < 3.00 | NO-GO：暂缓，回到需求验证阶段 |

### 3.3 判定结论

> **判定结果：条件性 GO（加权总分 3.45 / 5）。**
>
> **判定要点（关键结论）**：
> 1. **需求是真实的，差异化空间是存在的，但"经济性"是最大的未解风险。** 需求真实性（4.0）与竞争差异化（4.0）支撑了 GO 的方向；**单位经济性（2.5）是唯一低于 3 分的维度，也是唯一可能推翻整个方案的因素。**
> 2. **因此不批准全量立项，只批准"单场景最小验证"。** 建议规模：**≤ 6 周、≤ 3 人、单一场景（P3）、单一数据集**。
> 3. **投入结构建议"轻图谱、重链路"**：先把**解析 → 抽取 → 实体消解 → 溯源引用**这条主干做扎实（这是所有场景的公共资产），图谱存储与多跳查询按 P3 的最小需求实现，**不为未来可能用不到的场景过度设计图谱**。

**批准条件（三条必须同时满足，缺一即降级为 NO-GO）**

| # | 条件 | 度量 | 验证方式 |
|---|---|---|---|
| **C1** | **图谱带来不可替代增益** | 图谱版相对纯 RAG 基线在"隐性关联召回 / 多跳答对率"上提升 **≥ 10%** | P3 最小实验的 A/B 对照（同一数据集跑 RAG 基线 vs 图谱版） |
| **C2** | **质量达到可用线** | 隐性关联召回 **≥ 0.80**、误报率 **≤ 0.15**、**答案引用覆盖率 = 100%** | P3 最小实验（200 合同 + 500 发票 + 100 凭证，20 组植入关联） |
| **C3** | **单位成本可接受** | 单份文档的"解析 + 抽取 + 图谱构建"成本落在预设阈值内，且**增量更新成本显著低于全量重建** | 成本基准测试（用 `*_mvp/` 目录承载），产出每千页文档的成本曲线 |

**反证条件（出现任一即停止投入或降级）**

| # | 反证条件 | 应对 |
|---|---|---|
| **F1** | 图谱版相对 RAG 基线的增益 **< 10%** | **判定该场景"不需要图谱"，退回 RAG-first 产品形态**，从路线图移除图谱依赖 |
| **F2** | 多跳答对率 / 影响面召回 **< 0.80** | **暂缓图谱化投入**，优先补齐抽取与实体消解质量 |
| **F3** | 引用覆盖率 **< 100%** | **直接 NO-GO**（该场景的用户对不可溯源答案零容忍，产品无使用价值） |
| **F4** | 单位成本无法收敛到可接受区间 | **降级为"仅解析 + 结构化抽取"的轻量产品**，放弃图谱问答定位 |
| **F5** | 目标客户访谈显示"付费意愿 < 替换现有工具成本" | 重新评估 1.3 权重中"付费意愿"维度，重算 Top 5 排序 |

### 3.4 验证里程碑

| 阶段 | 周期（建议） | 关键动作 | 出口判据 |
|---|---|---|---|
| **M0｜假设澄清** | 第 1 周 | 5–8 家目标客户深访（A1 / A7）；确认私域部署是否硬需求（A12） | 产出付费意愿结论；**若付费意愿不成立 → 立即 NO-GO** |
| **M1｜解析实测** | 第 1–2 周 | 用 P3 样本实测 MinerU 对表格 / 扫描件 / CSV 的还原质量（A3） | 关键字段抽取准确率达到可用线 |
| **M2｜抽取实测** | 第 2–3 周 | 用 200 条 gold 关系评测 LangExtract 中文 precision（A4） | precision ≥ 0.85（不达标先调 Prompt 版本，**禁止原地覆盖历史版本**，遵循 `prompts/` 版本管理规范） |
| **M3｜图谱 vs RAG 对照** | 第 3–5 周 | 跑 P3 最小实验，同时跑 RAG 基线（条件 C1 / C2） | 增益 ≥ 10% 且质量达 C2 |
| **M4｜成本基准** | 第 4–6 周 | 千页文档成本曲线 + 增量 vs 全量对比（条件 C3） | 单位成本落入阈值 |
| **M5｜判定收敛** | 第 6 周 | 汇总 C1–C3 与 F1–F5 | **输出终态：GO / 条件性 GO 续期 / NO-GO** |

> **关键结论：本阶段的一切动作都服务于"以最低成本证伪"。** 任何一条反证条件成立，都应在 6 周内主动止损，而非靠增加投入试图翻盘。

**立项前必须完成的三项（任一不达标，Top 5 排序需整体重算）**：**A1（付费意愿访谈）、A3（解析质量实测）、A4（抽取质量实测）。**

## 附录 B. 证据分级说明

为便于复核，本报告对每条判断标注证据等级：

| 等级 | 含义 | 处理方式 |
|---|---|---|
| **E1｜公开事实** | 可从产品官方文档、公开定价页、公开仓库核实的客观信息 | 可直接引用，标注来源与年份 |
| **E2｜行业共识** | 多个公开来源一致、无争议的行业判断 | 可引用，标注"行业共识" |
| **E3｜领域推理** | 基于产品机制与架构推导出的判断，无直接公开证据 | **必须标注置信度**（高 / 中 / 低） |
| **E4｜待验证假设** | 影响结论但当前无法核实，需通过实验或访谈确认 | **必须标注置信度并给出验证方式** |

> **原则：严禁编造精确市场规模、增长率、定价、市占率等数字。** 凡无法核实者，一律降级为 E3 / E4 并显式标注。本文的竞品能力矩阵单元格均为 **E3**，其符号（✅ / ⚠️ / ❌ / ❓）表示**能力覆盖程度**，不代表实测结论。
