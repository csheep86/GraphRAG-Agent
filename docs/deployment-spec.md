## 0. 当前缺口（写在最前，不粉饰）

2026-09-27 实测：**当前仓库不具备私有化交付能力**，两处硬缺口必须补上。
**进展（2026-09-30）**：**D-2 迁移基线已在 Sprint 9.7 兑现**；**D-1 拆两半**——「compose 起全套」**已在 Sprint 10.3 兑现**（backend / frontend / Neo4j 三服务 `up` 全 `healthy`，PG 位留空，**P1 切 PG（DR-B1）时一并就位**），**离线镜像包归 P1**（DR-A6）。

⇒ 判据不变：**在 D-1 的镜像包补齐前，对外仍不得承诺"可私有化交付"**（不能拿"能起来"冒充"能交付"）。

## 1. 交付形态与边界

### 1.1 交付形态

**单机 `docker-compose` 编排**——**一套 compose = 一个租户**（ADR-0007 §3.3）；数据不出客户网络。

> **口径修订（2026-10-01，用户澄清）**：本节原写「客户机无外网，不能 `docker pull`」**与事实不符**——客户通常购买**云主机**部署，**有出网**。⇒ 改为**双模式**按下表选；**云主机客户默认走 registry**。

| 模式 | 适用客户 | 镜像获取 | 补丁体感 |
|---|---|---|---|
| **registry**（默认） | 云主机 / 有出网 | `docker compose pull`（可指向客户内网已有私有 registry，或我方 registry） | **只传变化层**（数 MB），接近传统"打补丁" |
| **离线 tar**（保留） | 真内网 / 集团机房（无出网） | `docker load -i <包>.tar` | 全量传输，较慢 |

| 交付物 | 形态 | 说明 |
|---|---|---|
| 编排文件 | `docker-compose.yml` + `.env.example` | 唯一安装入口；**用 `image:` 拉版本化镜像，不用 `build:` 现场构建** |
| 镜像 | `<registry>/<组件>:<base_version>-<variant>` | 变体镜像（ADR-0007 §3.2）；tag 固定小版本，遵守 D-N（`:latest` 是不可复现的同义词） |
| 变体清单 | `deploy/variants/<客户>.yaml` | 声明启用的插件与配置；**不含业务代码** |
| 部署手册 | 本文 + 安装步骤附录 | 交付时随包提供 |
| 备份 / 恢复脚本 | `deploy/backup.sh` / `deploy/restore.sh` | §7 |
| 升级说明 | 版本 Release Notes + 迁移清单 | §8 |
| License 文件 | `*.lic`（客户自行放入） | ADR-0006 §2.2 |

> **不做运行时热插拔**：插件在**构建期烘焙**进镜像（ADR-0007 §3.1），客户现场不装插件——这是既定取舍，换取**零状态漂移**。售前须讲清。
>
> **子公司物理隔离**：客户要求各子公司数据物理分开时，**多起几套 compose 即可，不改代码**（ADR-0003 §3.7 裁决二）。

### 1.2 不做（明确）

- **不做** K8s / Helm（企业级编排属 v2.0 之后，TBD-D2）；
- **不做**多活 / 跨机房容灾（单机交付，靠备份恢复）；
- **不做**公有云托管版（与"数据不出内网"冲突）；
- **不做**客户现场编译（必须离线镜像，禁在现场 `pip install`）。

## 3. 配置与密钥

| 项 | 规则 |
|---|---|
| 配置来源 | `.env.example` → 现场复制为 `.env`；**`.env` 禁止入库**（已在 `.gitignore`） |
| 密钥注入 | 部署时**生成并注入**，禁止写进镜像、禁止进 git、禁止出现在日志 |
| 必配密钥 | PG 密码、Neo4j 密码、`SECRET_KEY`、**`LICENSE_PUBLIC_KEY`**（ADR-0006 §3.2）、LLM Key（内网可空） |
| **生产默认值** | **`PRIVATE_DEPLOY_ENABLED=true`**（PRD H6 私域禁外发）——**生产环境不得为 false** |
| 敏感日志 | 脱敏后写（PRD H5）；License 正文 / 签名**禁止**进日志（ADR-0006 §2.5） |

## 4. 离线安装

### 4.1 前置检查（安装前必做，逐条勾选）

```
[ ] 1. 资源达标（见 §5）
[ ] 2. 端口未被占用（3000 / 8000；5432 / 7687 仅内网）
[ ] 3. 磁盘：数据卷所在分区 ≥ 规划容量的 2 倍（备份需要空间）
[ ] 4. 时钟已校准（无 NTP 环境手工校时 —— ADR-0006 §2.7 依赖）
[ ] 5. Docker / Compose 版本满足镜像要求
[ ] 6. 镜像离线包已导入（docker load）且 SHA-256 与清单一致
[ ] 7. License 文件已就位（ADR-0006 §2.2 第 5 步）
```

### 4.2 安装步骤

```text
1. docker load -i <镜像包>.tar          # 导入离线镜像
2. cp .env.example .env 并按现场填写    # 密钥在此生成
3. 放置 license 文件到 LICENSE_FILE_PATH
4. docker compose up -d                 # 起全部服务
5. 冒烟验证（见 §9）
6. 跑一次备份并验证可恢复（见 §7.4）
7. 交付签署：安装验收清单（§9）逐条签字
```

> **禁止**现场 `pip install` / `npm install`：依赖必须 baked 进镜像（D-1 补齐方式）。

## 5. 资源规格

| 档位 | CPU | 内存 | 磁盘（数据卷） | 适用 |
|---|---|---|---|---|
| **最小（试点 / POC）** | 8 核 | 32 GB | 500 GB | ≤ 5 千份文档、单租户演示 |
| **推荐（生产）** | 16 核 | 64 GB | 2 TB 起（按语料增长） | 正式上线 |

> 内存分配建议（**范围值，须按实测调**）：Neo4j heap 占 30%~40%、page cache 占 20%~30%；PG `shared_buffers` 占 20%~25%。
> **容量主驱动是 Neo4j 图规模与 chunk 数**，不是文档份数 ⇒ 交付前须按客户实际语料实测，不得按"文档份数"线性外推。

## 6. 备份与恢复

### 6.1 备份对象（**缺一不可复现**）

| 对象 | 方式 | 为什么必须 |
|---|---|---|
| PostgreSQL | `pg_dump`（custom format） | **Source of Truth**（ADR-0002） |
| Neo4j | `neo4j-admin database dump` | 图数据 |
| 文件存储 | `/data/storage` 目录（rsync / tar） | 原件与切片 |
| License 文件 | 复制 | 恢复后必须能继续启动 |
| 配置 | `.env` **脱敏副本**（去密钥） | 便于重建配置 |
| **active `kg_version`** | **记录到备份清单** | 见 §6.2 |

### 6.2 一致性（关键约束）

PG 是 Source of Truth、Neo4j 是从属镜像（ADR-0002）。因此：

1. 备份必须**记录备份时刻的 active `kg_version`**（写进 `backup-manifest.json`）；
2. 恢复后必须校验：**PG 的 active 版本 == Neo4j 中该版本的节点存在**；版本错位即"幽灵版本"（ADR-0002 明令禁止），**必须报错而非静默启动**；
3. 备份窗口内**停止写入**（或停服），避免"备份期间新版本已 active 但图未写完"。

### 6.3 频率与指标

| 项 | 建议值 | 备注 |
|---|---|---|
| 备份频率 | 日增量 + 周全量 | 全量含 Neo4j dump |
| 保留 | 日备 7 份 / 周备 4 份 | 按客户合规要求调 |
| **RPO** | ≤ 24 h | **待客户确认**（TBD-D3） |
| **RTO** | ≤ 4 h | **待客户确认**（TBD-D3） |

### 6.4 恢复演练（**不演练 = 没有备份**）

> **「独立环境」的定义**（2026-10-03 裁决，全文见 `changes/P0-m6-eval/integration-log.md` **L10-ENV**）：
> 本节与 §10 第 9 项所称"独立环境" = **交付演练环境**，三条判据：
> ① **从交付物部署**——部署命令里**无 `build:`**，只有 `image: <固定 tag>`（**非 `latest`**），
> 且该 tag **就是要交付给客户的那个**（**客户拿不到源码** ⇒ 从源码起的演练**证明不了客户能装上**）；
> ② **独立度**——独立 compose 项目 + **独立数据卷 / 端口 / `.env`**；
> **复用开发机现有服务不算独立**（有开发残留 / `.env` 污染 / 已建好的图）；
> ③ **执行人 ≠ 写部署脚本的人**，须**一人执行、一人见证**并共同署名——
> 自己写的脚本自己验收 = **自证**，是最弱的证据。
> 留证落 **`docs/drills/`**，命名 `restore-drill-<日期>.md` / `install-acceptance-<日期>.md`，
> **必须显式标注「内部演练，非客户现场验收」**。
> ⚠️ **术语分流**：**G-9** 语境的"独立环境"（能起 Neo4j 的临时环境）另称**图谱验证环境**，
> 二者**不是一回事**，不得混用。

- 判据：**每季度至少一次**恢复演练，在**独立环境**恢复并跑通 §10 冒烟，记录 `restore-drill-<日期>.md`；
- 每次备份产出 `backup-manifest.json`：各文件 **SHA-256** + 大小 + 时刻 + active `kg_version`；
- 恢复后校验清单：服务起 → health 200 → License 状态正常 → 抽样 1 条文档可查 → 抽样 1 次问答有引用 → 跨租户隔离仍生效。

## 7. 升级与迁移

### 7.1 迁移工具（**D-2 的处置**）

> ⚠️ **2026-10-01 更正**：~~必须引入数据库迁移工具（建议 Alembic）~~ **Alembic 基线已引入并已建**（**DR-E1**：依赖 + 基线迁移 `00f44b912817` + 等价性测试钉死「加表必写迁移」）。**剩余缺口不是"要不要引入"，而是「逐版本可幂等迁移纪律」+「升级演练」**（DR-E1 纪律 / DR-E3 演练，归 **P6**）。以下三条是当初的立项理由，保留备查。

理由：

1. `create_all` 只建新表、**不改旧表** ⇒ 升级后旧库缺列，错误在运行时才暴露（已在生产环境即为事故）；
2. 客户现场无法"删库重来"（数据即客户资产）；
3. 无迁移脚本 ⇒ 无法回滚，升级失败即长时间停服。

迁移纪律：

| 项 | 规则 |
|---|---|
| 每个版本 | 必须带对应迁移脚本（**版本 → 迁移脚本一一对应**） |
| 迁移脚本 | 必须**可重复执行**（幂等）且**记录版本号** |
| 禁止 | 手工改客户库表结构（一律走迁移脚本） |
| **过渡期** | **D-2 未补齐前，升级只允许"全新部署 + 数据导入"，严禁原地升级** |

### 7.2 升级步骤

```text
1. 备份（§6）+ 校验可恢复            ← 不备份不升级
2. 停服（docker compose down）
3. 取目标版本镜像：
   - registry 模式：docker compose pull      ← 只传变化层
   - 离线模式：docker load -i <新包>.tar
4. 执行数据库迁移（Alembic upgrade head）
5. 起服（docker compose up -d）→ 冒烟（§10 第 1~6 项）
6. 记录：版本 / 迁移号 / 耗时 / 是否回滚
7. 失败即回滚：改 tag 回上一版本 + 恢复备份
   （迁移无 down 脚本时不承诺"回滚迁移"）
```

> **回滚优先改 tag**：镜像版本化 ⇒ 回滚只需把 `image:` 的 tag 改回上一版本并 `up -d`，**不必**重新导入旧包。这是 registry 模式相对离线模式的额外收益。

### 7.2.1 补丁（版本号第三位 **PATCH**）三条纪律

> **版本语义完整定义见 `delivery-requirements-and-guardrails.md` §7**：`app_version` = `MAJOR.MINOR.PATCH`；**`base_version` = MAJOR**；补丁 = **第三位 PATCH**（当前 `1.6.0` 的补丁 = `1.6.1`）。

补丁 = 只修 bug。**打补丁时以下内容不得变更**（ADR-0007 §3.8.3）：

| # | 纪律 | 机器判据 |
|---|---|---|
| 1 | **不改** `contracts/openapi.yaml` | `export_openapi.py --check`；PR 出现 diff 即红 |
| 2 | **不改** ADR-0004 八个接缝的接口签名 | 接缝签名快照测试（ADR-0007 §3.9）：**PATCH / MINOR** ⇒ 快照**逐字相同** |
| 3 | 数据库只允许**向后兼容的加法** | Alembic 迁移评审 + 升级演练 |

需破坏性变更 ⇒ **升 MAJOR（大版本）**：

- `1.x` → `2.0.0` 时 **`base_version` 由 1 变 2** ⇒ **插件失效、需重新开发**；
- 这属**商业事件**而非技术事件 ⇒ **该事实须写进首份商业合同**，避免"免费重做插件"的预期落差；
- 届时须在 release notes 列出**全部** `breaking` 项。

### 7.3 升级检查清单

```
[ ] 目标版本的迁移脚本存在且已评审
[ ] 备份已完成且 manifest 完整
[ ] 回滚方案（**上一版本 tag** + 备份路径 + 预计耗时）已写明
[ ] License 对新版本仍有效（模块 / 有效期 / 席位，ADR-0006 §2.4）
[ ] 升级后 active kg_version 未错位（§6.2）
[ ] **补丁位升级**：已确认未改契约 / 未改接缝签名（§7.2.1 三条纪律）
[ ] **变体客户**：目标 tag 的 `-<variant>` 后缀与 `deploy/variants/<客户>.yaml` 一致
```

## 9. 运维与可观测

> **第一原则**：离线环境的监控**不能假设客户有 Prometheus**。客户内网通常已有监控平台（Zabbix / Prometheus / 厂商专有），且未必允许我们另起一套 ⇒ 交付策略是**"可被采集"**，而非自带全家桶。

### 9.1 必须提供的可采集面

| 面 | 内容 |
|---|---|
| 健康检查 | `GET /health`（compose `healthcheck` 直接消费）；存活 / 就绪是否分离见 **TBD-D5** |
| **License 状态** | `GET /license/status`——**运维第一现场**：四维度 + 剩余天数 + 指纹是否匹配 |
| 结构化日志 | loguru JSON 落卷 + 轮转（logrotate）；字段含 `trace_id`；**禁止**输出密钥 / License 正文 |
| 容器状态 | `docker compose ps` / 退出码 |

### 9.2 告警项（最小集）

| 告警 | 判据 |
|---|---|
| 磁盘 | 数据卷 + 备份卷使用率 > 80% |
| 容器 | 非正常退出 / 重启 |
| 备份 | 备份失败或 `backup-manifest.json` 校验不过（§6） |
| **License 即将过期** | 剩余 < 30 天 |
| **License 拒绝激增** | `license.denied` 短时暴涨 ⇒ 要么配置误伤、要么在被尝试绕过，**必须查** |
| 时钟回拨 | `license.clock_skew`（ADR-0006 §2.7） |

### 9.3 容量

- 主驱动是 **Neo4j 图规模与 chunk 数**（不是文档份数）⇒ 交付前按客户实际语料实测，**禁止按份数线性外推**（§5 已述）；
- 扩容方式：**垂直扩容**（单机交付，不做水平分片）；
- 容量告警阈值须实测后登记，**不预设数字**。
