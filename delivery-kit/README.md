# delivery-kit · 交付资料包

> **用途**：面向三类不同读者的对外交付文档，从同一份代码事实出发，口径递增。
> **代码事实来源**：`backend/`、`frontend/`、`contracts/openapi.yaml`、`deploy/`、`tests/`
> **基线版本**：`app_version = 1.6.0`（见 `backend/app/core/config.py:129`）
> **生成日期**：2026-10-10

---

## 为什么叫 delivery-kit

三份文件不是"三版说明书"，而是一套**配套配件**——缺任何一份，对外动作都做不完整：

| 场景 | 取哪一份 |
|---|---|
| 做海报、写推文、做融资/推介 PPT、准备演示讲稿 | **01** |
| 签合同前逐条核对"到底交付什么"，做验收谈判 | **02** |
| 客户 IT 部门做技术评审、安全审查、部署容量规划 | **03** |

`delivery-kit` 把它定位成"随时可取用的一整套"，而不是又一个文档目录。

## 三份文档与格式选择

| 文件 | 格式 | 为什么是它 |
|---|---|---|
| `01-宣传素材包.md` | **Markdown** | 主要消费者是 **AI**（生成海报 / 文案 / PPT / 讲稿）。Markdown 的标题层级、表格、列表在喂给 LLM 时**结构无损**；若用 Word/PDF，AI 解析时表格和层级容易塌成一坨。要出 Word/PDF 是**下游动作**，由生成结果的 AI 去做。 |
| `02-签约功能清单.xlsx` | **Excel** | 合同附件要能**逐行勾选、留批改、导 PDF、双方签字**。功能清单天然二维，Excel 最低摩擦。多 Sheet 把"含 / 不含 / 怎么验"分开，避免口头扯皮。 |
| `03-技术规格说明书.md` + `.docx` | **双份同源** | `.md` 用于入库做版本 diff、喂 AI 二次加工；`.docx` 用于客户 IT 流转评审（批注、盖章、套模板）。内容一致，`.docx` 为分发产物。 |

> 第二份用 Excel 是用户指定；其余两份按上述理由选择。

## 口径纪律（**务必先读，再对外**）

本项目长期存在"文档说没做、代码已做了"（或反之）的口径漂移风险。本套文档的**每一条宣称**都回溯到代码事实，三条硬规则：

1. **可交付** = 代码里真的存在，且能指出 `文件:行号`。
2. **有限定语** = 功能存在但能力有边界（如"无按角色筛选"），对外必须连带说明。
3. **不承诺** = 占位页 / 规划中 / 契约有端点但无 UI，一律不进宣传与签约口径。

三份文档的"禁止夸大"力度不同：

| 文档 | 允许修辞的程度 | 边界处理 |
|---|---|---|
| 01 宣传 | **允许**价值修辞与营销语言 | 禁用口径见 §09 红线清单，不得越过 |
| 02 签约 | **禁止**任何修辞，只写可验收事实 | 每行都带"验收方式"与"可否演示" |
| 03 技术 | **禁止**修辞，含已知缺陷与债务 | 逐模块标注成熟度 |

## 生成方式（可复现）

```powershell
cd backend
# Excel
uv run --with openpyxl      python ..\delivery-kit\scripts\build_contract_xlsx.py
# Word
uv run --with python-docx   python ..\delivery-kit\scripts\build_tech_docx.py
```

> 依赖经 `uv run --with` **临时环境**安装，**不写入** `pyproject.toml` / `uv.lock`，
> 不污染项目依赖基线（守 `CODEBUDDY.md` 环境与依赖规则）。
