# 技能名称：test-driven-development（测试驱动开发）

## 用途
通过"红-绿-重构"循环保证每一段业务逻辑都有测试覆盖，并让测试成为行为的第一个使用者，倒逼接口与数据结构设计合理。

## 触发条件
- 新增业务逻辑（后端 Pydantic 模型 / 接口 / 异步任务，前端组件 / hooks / 工具函数）。
- 修复 bug（先写复现测试，再修复）。
- 用户要求 TDD 或按项目规范为改动补充测试。

## 执行步骤
1. **确认行为**：明确当前要实现的可验证行为，写出测试名（描述行为，如 `test_upload_returns_task_id`）。
2. **红**：先写测试并运行，确认其失败且失败原因符合预期（而非环境 / 导入错误）。
3. **绿**：写最小实现让测试通过，不多写一行超出当前行为的代码。
4. **重构**：在测试全绿的保护下清理实现与测试代码（命名、去重、格式化）。
5. **放置测试**：按层级放置——单元 `tests/unit/`、集成 `tests/integration/`、端到端 `tests/e2e/`；前端测试与被测文件同目录。
6. **循环**：下一个行为回到步骤 1。

## 输出格式
- 每轮循环：测试名 → 红（失败摘要）→ 绿（通过摘要）→ 重构说明
- 涉及接口时：测试所依据的契约字段（来自 `contracts/openapi.yaml`）
- 最终：新增测试清单与覆盖率说明
