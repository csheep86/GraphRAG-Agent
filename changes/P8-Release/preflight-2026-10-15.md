## 2. ⚠️ 自我订正：**首版把 P7-H 判成「未开工」，判错了**

### 2.1 错在哪

首版用的判据是「**`changes/P7-H/` 里有没有 `integration-log.md`**」⇒ 没有 ⇒ 判「未开工」。

**这是拿代理指标当结论。** P7-H 是**双人演练批次**，它的产出物本来就不是
integration-log，而是 **`docs/drills/` 下的演练留证**（proposal §4 出口判据 1-3 写的就是它）。
留证**确实存在**，只是没人往 `changes/P7-H/` 里写日志。

### 2.2 为什么这条要单独记一笔

这正是 **P7-R 那条教训的翻版** —— P7-R 的教训是「**测错对象，换再多次判据也不会对**」；
这次是「**拿'有没有文档'当'做没做'，而不是去看那件事自己的出口判据**」。
两者是同一种病：**用容易拿到的信号替代真正要验的东西**。

⇒ **后续核任何批次是否完成，一律回到该批次 `proposal.md` 的「出口判据」逐条核，
不许用「有没有 integration-log / 有没有目录 / 文档里写没写 ✅」来代理。**

- 第 4 条由 ❌ 改 ✅ ⇒ P8-Release 的前置**比首版乐观一项**；

## 5. 路 A / 路 B 的机械查证（2026-10-15）

> P7-K §10.4 把方向登记为「确认采样确已钉 0，再查供应商侧是否承诺逐字稳定」，
> 并自注「**未经查证，仅登记方向**」。本节把它**查实**，方法全部可复跑。

### 5.1 逐环节排查（**每一环都有读数，不是推断**）

| 环节 | 是否确定 | 机械证据 |
|---|---|---|
| 采样参数 | ✅ 已钉死 | `providers/llm.py:75` `temperature=0` **硬编码**；P6-R 裁决 O1 明写「**不留配置开关**」；`max_retries=0`，无 `top_p` |
| prompt 内容 | ✅ **逐字一致** | 连跑两次，拦截 `AgentService._chat.ainvoke`（`agents.py:639`）前 dump 全部 messages：2 段、**61851 字符**，两次**完全相同** |
| 子图选择 | ✅ 确定 | `_query_subgraph_node_index()` 有 `ORDER BY degree DESC, id`；`select_subgraph_nodes` docstring 明写「**同输入必同解**」 |
| 注入证据序列 | ✅ **1.000** | P7-S 实测（32 条逐位相同） |
| 供应商（短 prompt） | ✅ 确定 | 同一短 prompt 调 3 次 ⇒ **逐字一致** |
| **供应商（长 prompt）** | ❌ **不确定** | **真实 prompt（61851 字符）调 3 次 ⇒ 3 次全不同**（len 636 / 791 / 719） |
| **`seed` 能否救** | ❌ **无效** | 加 `seed=42` 再调 3 次 ⇒ **仍 3 次全不同**（len 410 / 572 / 439）⇒ DeepSeek 忽略该参数 |
| **要点覆盖一致率** | ✅ **1.000** | P7-S 实测 |

### 5.2 结论：漂在哪

**不在采样、不在 prompt、不在检索、不在子图 —— 在供应商的长上下文推理。**

`temperature=0` + 短 prompt ⇒ 确定；**同一个模型、同一个 temperature、同一个 prompt，只因为变长（62k 字符）就 3/3 不同。**
这是服务端 MoE 路由 / 动态批处理 / 长上下文 kernel 的非确定性，不是本项目能控的（`seed` 已证无效）。

### 5.3 ⇒ 判断：**选路 B**（改判据口径，不是"降标准"）

| 选项 | 可行性 | 代价 |
|---|---|---|
| **路 A-a 换供应商 / 模型** | 未验；需重新跑全套验收 + 成本 / 合规重评 | 高 |
| **路 A-b 缩短 prompt** | 可能回到确定性区间，但**喂给 LLM 的证据变少** ⇒ 直接冲击 C1（图谱增益）等指标 | **质量换确定性** |
| **路 A-c `seed`** | ❌ **已证无效** | — |
| **路 B 判据改「逐字一致」→「语义/要点一致」** | ✅ **立刻成立** —— 要点覆盖一致率已实测 **1.000**，零工程改动 | 判据严格度下降 |

**推荐路 B，理由是实测，不是妥协**：
语义层面系统**本来就是稳的**（1.000），只有措辞在漂。
「连跑两次答案逐字一致」这条判据要求的是**传统软件的确定性**，对 LLM 系统本身就不成立 ——
它是 P7-K §10.3 已证否的东西，现在又多了一条物理原因（长上下文不可控）。

⚠️ **必须说清的代价**：这**确实是降口径**（逐字 → 语义）。
且「语义一致」本身**需要一个机械判据**（不能拍脑袋）——目前 P7-S 用的是粗糙字符串 / 数字匹配，
**不等于** rubric-v2 人工判分 ⇒ 这条落地时还得定一次口径。

### 5.4 ⚠️ 本节的边界（不许外推）

- 长 prompt 实验**只跑了 3 次 × 1 个 prompt**（1 道题）。够定「是不是确定」，**不够定漂移幅度**。
- 未验证 **缩短到多长**能回到确定性区间 ⇒ 路 A-b 的代价目前**无法量化**。
- 未验证其他供应商 / 模型（换供应商要重新跑全套验收）。

### 5.5 复跑方法（¥0 到 3 次 LLM 调用）

1. 起 `graphrag-pg` / `graphrag-neo`，`DATABASE_URL` 指向 **`graphrag_eval`**（有数据的库）；
2. 把 `AgentService._ensure_chat` 打成返回 fake chat（其 `ainvoke` dump messages 后抛异常）
   ⇒ **不真调 LLM**，跑两次 dump prompt 做逐字 diff；
3. 拿 dump 的真 prompt，用 `build_chat_model()`（或加 `seed`）调 3 次，比输出。
