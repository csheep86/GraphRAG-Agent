## 1. 为什么现在做

需求基线开篇就写明一条纪律（§0 第 4 条）：**"`✅ / 🟡` 会过期，别拿它当结论"**——
护栏大半是 `xfail` 骨架，`pytest 全绿 ≠ 护栏在拦`。但过去四个批次（P2 / P2.5 / P3 / P6）
每批只 delta 更新自己动的那一两行 G，**没有人做一次全量对账**。后果已经在文档里显形：

| # | 症状 | 位置 |
|---|---|---|
| 1 | G-10 已摘 xfail 转正（P3-A），但 §2.2 状态列**仍写「🟡 骨架已就位 / xfail 挂起」** | 需求基线 §2.2 G-10 行 |
| 2 | §3.1 B6 行仍写「仍缺 `documents` / `qa_logs` / `storage_key`（P3 补齐）」，实际 P3-B 已补齐 | 需求基线 §3.1 B6 行 |
| 3 | §3.1 B11 行仍写「待建；**CI 无 Neo4j**」，实际 P3-B 已起 `neo4j:5.26-community` 并 5 条真图用例进 CI 必过 | 需求基线 §3.1 B11 行 |
| 4 | §5 的 pytest 基数仍是 P1-C 时代的 **707 passed**，实际已 **930 passed** | 需求基线 §5 |

⇒ 这不是"文档没来得及更新"的小事：**顺着 §2.2 / §3.1 读的人会得出两条相反结论**，
而这两处恰恰是"谁对外宣称达标"的引用源。**先对账，再谈后面四个阶段怎么排。**

## 3. 不做什么（**本批边界 = Non-goals**）

1. **不改产品代码**（`backend/app/**` / `frontend/src/**` 一律不碰）。
2. **不开新功能**——License 子系统、第二个 variant、文档登记门禁，一律只登记不实现。
3. **不改契约**（`contracts/openapi.yaml` 零 diff）。
4. **不动评测口径与阈值**（C1 的 10%、C2-a 的 0.80、C2-b 的 0.15、`refusal_false_refusal` 的 0、`EVAL_SINGLE_DOC_TOKEN_CEILING` 32000 全部不动）。
5. **不顺手修发现的小 bug**（如 `test_frozen_snapshot_is_committed` 名实不符）——**只登记**，留给它所属的需求条目。
6. **不改 `check_startup_readiness.py` 本身**：它虽然被查出两个结构性盲区（§5），
   但改它会改变 CI 报告口径，且要连带给它加自测 ⇒ **留作独立批次 P7-B**，不在本批顺手做。
7. 不改 `ci.yml`（本批不新增门禁步骤）。

## 4. 出口判据

1. 逐条 G 的**档位 + 证据路径 + 转正动作 + 优先级**四要素齐全；
2. T1 / T2 的判定**由实跑得出**（PG 16.x + 受限角色），不是读代码得出的；
3. 需求基线状态列与机器结论**一致**（订正处显式标注 2026-10-05 对账）；
4. 全部门禁绿且 `pytest` passed **不减**（本批未改代码 ⇒ 仍为 930）；
5. `check_session_drift` S1 报出 Non-goals 且 S2–S5 无命中。
