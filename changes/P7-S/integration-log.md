## 5. 判别实验：读数与结论

### 5.1 命令（一条）

```bash
cd backend
# DATABASE_URL 必须指向「后端进程实际使用的那个库」——见 §6
uv run python scripts/check_injected_evidence.py --repeat 3 --limit 3 \
    --out reports/eval/injected-p7s-<ts>.json
```

### 5.2 两轮读数（N=3，n=3，git `2c9b17a` + 本批改动）

落盘：`backend/reports/eval/injected-p7s-run1.json`、`injected-p7s-run2.json`

| 指标 | run1 | run2 |
|---|---|---|
| **注入序列一致率**（检索侧） | **1.000** | **1.000** |
| **答案逐字一致率**（生成侧） | **0.000** | **0.000** |
| 引用序列一致率 | 0.000 | 0.667 |
| 要点覆盖一致率 | 1.000 | 1.000 |
| 漂移题数（检索 / 生成） | **0 / 3** | **0 / 3** |
| 出口缺失题号 `missing_exit` | `[]` | `[]` |

逐题明细（注入条数 = 32，三轮完全相同）：

| 题 | 注入序列 | 引用条数（3 次） | 引用集合重复项 |
|---|---|---|---|
| #1 | 32 / 32 / 32（三轮逐位相同） | 6 / 6 / 6 | 无 / 无 / 无 |
| #2 | 32 / 32 / 32 | 1 / 3 / 3（run2: 1/1/1） | 无 / 无 / 无 |
| #3 | 32 / 32 / 32 | 3 / 7 / 7（run2: 7/7/7） | 无 / 无 / 无 |

### 5.3 三选一结论：**生成漂**

判据（机械比较，不掺判断）：

- **检索侧**：注入 prompt 的 chunk_id 序列在每题的 3 次之间**逐位相同**（一致率 **1.000**，两轮一致）
  ⇒ 证据基线**固定**，检索没有漂；
- **生成侧**：同一份证据、同一条链路，答案逐字一致率 **0.000**（3/3 题每题 3 次互不相同）
  ⇒ 漂移**在生成环节**；
- **引用序列跟着答案漂**（0.000 / 0.667）——这与 P7-R §6.1 的推断**一致**：
  `citations` 是 `parsed.evidence` 的投影，而 `_grounded_citations` 又按「答案凭据是否逐字出现」过滤
  ⇒ **citation 集合是答案文本的函数**，所以它只能作为生成侧的**下游读数**，
  **不能**当检索侧的证据。

⇒ **P7-R §5.1 那句「根因在检索侧，去改检索是白费劲那句作废」应再作废一次**：
真正判不开的不是检索，是**拿 `citations` 当检索输出**这件事（P7-R §6.1 已预警，本批给的是**实测**）。

### 5.4 边界（不许外推的部分）

- n=3 / N=3 ⇒ 每个率带着**至少 ±1 题**的抖动。本轮只够定「**是不是 0**」：
  注入 1.000（不是 0）与答案 0.000（是 0）两轮**恒定** ⇒ 结论够用；
  要把它定成"是多少"得加题量（烧 LLM，属下一段）。
- **要点覆盖一致率 1.000** 用的是粗糙的字符串 / 数字匹配
  （与 `check_answer_stability.py` 同款），它**不等于** rubric-v2 的人工判分。

## 6. ⚠️ 环境发现（**直接影响证据可比性，必须登记**）

跑判别实验时发现两个 PG 库里 `kg_versions` 的 ready 状态**不一样**：

| 库 | 谁在用 | 最新的 ready 版本 | 该版本下的 `:Chunk` 数 |
|---|---|---|---|
| **`graphrag_eval`** | **运行中的后端实例（`127.0.0.1:8100`）** | `attendance-demo-v1` | **有**（实测注入 32 条） |
| **`graphrag`** | `backend/.env` 的 `DATABASE_URL` 默认值 | `20261012T064951Z-inc-569555ad` | **0** |

两条推论：

1. **P7-R §6.4「内部复现检索路径失败」的真因就在这里**——内部脚本按
   `backend/.env` 连的是 `graphrag` 库，那里最新 ready 是个**增量版本**，
   其下 `:Chunk` = 0 ⇒ `fetch_evidence_chunks` 恒返回空 ⇒ **不是"用错版本"，是连错库**。
   （P7-R §6.4 的「active 版本下 `Chunk -[:MENTIONS]-> Entity` = 0」
   这条**已作废**，它测的是那个空增量版本，不是 `attendance-demo-v1`。）
2. 在 `graphrag` 库上跑出的任何问答读数**都是假的**（注入序列恒空）。
   ⇒ 探针脚本已把这条写进 docstring，且**出口缺失时会显式打印 `missing_exit`**，
   不静默给"稳定"结论。
