## 0. 前提：部署形态由用户裁决为「一家一套」

这条裁决**缩小**了本批的范围，也顺带关闭了两条遗留：

| 结论 | 依据 |
|---|---|
| **不需要租户创建入口** | 一家一套 ⇒ 租户就是部署时的 `DEFAULT_ORG_ID`；`create_tenant` / `provision_tenant` 全仓零命中这件事，**对首客户不构成缺口** |
| **第 7 项（跨 org 被 RLS 拦截）在客户现场恒 SKIP** | 目标环境只有一个 org ⇒ 跨 org 无从验起。**这不是缺陷**，是部署形态决定的（隔离由物理部署承担），靠 pytest 的 G-26 子项兜底 |
| **F-P7G-1（第二租户）按"首客户不适用"关闭** | 同上；将来若出集团客户（一套部署装多家公司）需重新开批 |

## 1. 做了什么

**`backend/scripts/provision_admin.py`（新增）**，四个刻意的设计：

1. **不复用 `seed_dev_rbac.py`**：后者要求 `ALLOW_DEV_ORG_HEADER`（生产本就该 false），
   且只认默认 actor（`install_acceptance.py:538` 明写"只播 dev 默认 org"）⇒ 进交付包既不安全也说不通。
2. **口令不由脚本猜**：必须 `--password` 或 `--generate` 二选一，否则退出码 2。
   显式给的口令**不回显**；`--generate` 生成的**只打印一次**并提示当场保存。
3. **幂等**：账号已存在时重跑**不改口令**，只补齐 admin 授权；要重置须显式 `--reset-password`
   ⇒ 免得"再跑一次开户"把客户正在用的口令换掉。
4. **卡 License 席位**（`is_seat_available`）：超限**拒新增**，但按 ADR-0006 §2.5
   「卡增量、保存量」，**绝不锁已有数据**。
   ⚠️ 注意：无 License 时 `max_seats = 0` ⇒ 开户会被拒并给出明确原因
   （"先装 License 再开户"）⇒ 这是**正确**的失败，不是 bug。

文档：`docs/deployment-spec.md` §4.2 插入第 5 步（含命令 + 三条注意）。

## 2. 真跑读数

| 步骤 | 读数 |
|---|---|
| `--check`（账号不存在） | `[NG] 用户 p7p-probe-admin 不存在`，退出码 **1** |
| `--generate` 开户 | `[OK] 已创建用户 … admin 授权：已授予`，退出码 **0** |
| **重跑**（不给 `--reset-password`） | `[OK] 用户 … 已存在 ⇒ 未改动（重跑不会改口令）` ⇒ **幂等** |
| `--check`（现在） | `[OK] … 已存在`，退出码 **0** |
| **用生成的口令登录** | `POST /auth/login` ⇒ `token_len=279` |
| **带 token 调受保护端点** | `GET /api/v1/documents` ⇒ **200** |
| **错口令** | **401** `invalid_credentials`（后端统一回 401 且不区分原因） |

⇒ 判据不是"数据库多了一行"，而是**这个人真能登录并访问受保护资源**。

**交付环境可跑性已核实**：`backend/Dockerfile` 有 `COPY backend/scripts ./scripts` ⇒
镜像内有该脚本；交付 compose 里本来就有在容器内跑 `scripts/init_rls_roles.py` 的先例。
