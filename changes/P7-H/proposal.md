> **日期**：2026-10-13 ｜ **来源**：[`docs/release-readiness-audit-2026-10-13.md`](../../docs/release-readiness-audit-2026-10-13.md) §3 A5

> 🔒 **AI 不得单独收口**（`docs/delivery-plan.md` §9.3 第 2 条）：执行者 ≠ 见证者。

## 2. 做什么

1. **先裁决升级目标**：本批需先把 `app_version` bump（PATCH/MINOR 按 G-15 语义）到一个可回滚的前版本；**bump 本身在单独提交里做**，与演练动作分开。
2. 按既定双人流程执行：镜像起独立环境 ⇒ 升级 ⇒ 冒烟 ⇒ 回滚 ⇒ 恢复后校验（§6.2 必须过）。
3. 留证落 `docs/drills/upgrade-drill-<日期>.md`，**显式标注「内部演练，非客户现场验收」**。

## 3. Non-goals（**改一条都要先回来登记理由**）

1. **不在演练现场顺手修产品缺陷**——发现缺陷只登记编号与坐标，另立批次。
2. **不把 SKIP 写成 PASS**（第 9 项除外：它有明确的人工双人属性）。
3. **不动演示库数据**（不上传 / 不建图 / 不复写现有版本）⇒ 演练环境必须是独立卷。
4. **不做客户端环境的演练**（那是 v2.1+ 的事）。
5. **AI 不代签"见证者"那一栏**。

## 4. 出口判据

1. `docs/drills/` 出现**升级演练留证**，含回滚步骤 + 前后版本读数 + 恢复后 §6.2 结果。
2. 执行者 / 见证者**两个真名**，缺席任何一人 ⇒ 本批不得宣称完成。
3. 留证里有「内部演练，非客户现场验收」字样（缺了会被读成客户已验收）。
4. `pytest` 不降、CI 绿。

## 5. 升级用户的四种情况

1. **缺见证者** ⇒ 停在这里，保持未完状态，不许 AI 顶替。
2. bump 会触发契约重导 / `check_seams` 版本闸 ⇒ 先单独处理，别混在演练里。
3. 升级失败且原因在系统而非环境 ⇒ 停下报告，那是产品缺陷。
4. CI 红且复核两遍仍红 ⇒ 带 job 名 + 失败行 + 归因。
