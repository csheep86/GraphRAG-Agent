## 1. 目标（一句话）

把 M5 §3 验收 3 / §4.5 / §5.3 的**统一敏感字段脱敏工具 `mask(field, category)`** 从零做成真的：
八类敏感字段按 spec §4.5 的策略表脱敏，**接线到 `audit_log.detail` 写入前 + loguru JSON 日志出口两处**，
并用单元测试断言「**原文既不落库、也不落日志**」——断言对象是**已落库的 JSON** 与**运行期捕获的日志输出**，
不是 `mask()` 的返回值（后者是恒绿陷阱，纪律 **R-9**）。

三刀：

1. **`mask(field, category)` 工具 + 八类策略**：一个函数 + 一张策略表，严格照 spec §4.5 八行实现；
   salt 走配置 `mask_salt`；哈希类复用既有样板（`license/fingerprint.py:79` 的加 salt 形态），
   **文件名类复用 `documents.hash_filename`**（产出必须逐字节相同）。
2. **两处接线**：① `audit.py::record_audit_entry` 在写 `detail` **之前**；② loguru JSON 日志出口。
3. **同步测试 + 确认零契约漂移**：mask 是内部函数、不进 API ⇒ 用 `export_openapi.py --check` **证明**它没动。

## 2. 为什么是这一刀

- **它是 M5 目前唯一的缺口**：spec §1.1 五项目标里 ① RBAC ② 审计 + trace_id ④ 私域开关（P5-D 已做成）
  ⑤ 限流**均已落地**，只有 ③ 敏感字段过滤**零代码**（`grep -rn "def mask" backend/` 无结果）。
- **零 spec 升级**：spec **已把签名与策略写死**（§5.3 第三个统一组件原文「统一敏感字段脱敏工具函数
  （`mask(field, category)`）」+ §4.5 八类策略表）⇒ 实现它是**兑现已定稿的 spec**，不触发第 2 类升级。
- **排期队列里它现在最便宜**：`delivery-plan.md:198` 的 P5 顺序 `D4 → D2 M6 → D1 → D3/D5/D7/D8` 中，
  D4 / D1 / D3 均已收口，D2（M6）的第二批有**两道新的硬前置**（`applied` 枚举 + 契约同步五步、
  尚不存在的增量重算），D5 / D7 / D8 要么是大块算法活、要么要花真钱评测
  ⇒ **M5 收尾是当前唯一不需要先兑现另一个前置的目标**。

## 3. 明确不做（**11 条 Non-goals**，逐条对照）

1. **不实现 `alert` 表 / 限流告警联动**：spec §3 验收 5 自标 **P2**。
2. **不改 `specs/m5-permission-audit.md` / ADR**：规格齐全（签名 + 八类策略都在），要改 ⇒ 第 2 类升级。
3. **不动 RLS / RBAC / 租户隔离**：DR-B4 / DR-B9 各有门禁；本批只改「值怎么被记下来」。
4. **不碰 P5-C 的三个 ontology 端点与 `ontology_actions` 表**：偏离已裁决保留，不再"顺手订正"。
5. **不改 P5-D 的私域守卫（`app/core/egress.py`）**：上一批刚收口；本批不掺和网络层。
6. **不新增第三方依赖**：标准库 `hashlib` / `re` 即可。
7. **不做"可还原"**：mask 一律**单向**；哈希类加 salt 后不可逆，掩码类丢掉的部分不留旁路可供拼回。
8. **不改既有 `documents.filename_hash` 与 `:LegalPerson.id_hash` 的语义**：mask 的「文件名」类必须
   **产出同一个值**，不得另给一套。
9. **不重构 loguru 的日志配置**：只做脱敏接线；不用 patcher / filter 重写整套配置，**除非 D3 判定必需**
   并在 integration-log 登记理由。
10. **不做"自动识别字段类型"**：`category` 由调用方 / **登记表**显式给。让代码去"猜"哪个值是敏感字段
    ⇒ 漏判无处可追责，属典型 scope creep。
11. **不动前端 / 不动契约**（除非 D6 判定必需）：mask 是服务端内部行为。

## 5. 本批需要登记的**决策补充**（spec 未写清处，按第 2 类升级的处置顺序「先缩范围、后登记」）

| # | 冲突点 | 本批取法 | 登记理由 |
|---|---|---|---|
| **P5E-1** | 银行账号 / 电话的**策略列**写「仅保留后 4 位」，**示例列**却保留前段（`6228 **** **** 1234` / `138****1234`） | 取**示例列**形态（判据 1 要求逐字对偶）；中段一律掩码，尾 4 位是唯一可辨识尾段 | 示例是 spec 里唯一给出具体形态的一侧；且这两个示例正是国内通行脱敏形态（卡 BIN / 手机号段） |
| **P5E-2** | 合同金额示例 `1,234,567.89` → `***,***.00` 只有两组，而输入整数部分有三组 | 取**固定掩码** `***,***.00`（不随量级变化） | 按组数掩码会泄露**量级**（百万 vs 千元），量级本身即敏感信息；固定掩码同时逐字节等于 spec 示例 |
| **P5E-3** | 输入不足掩码所需长度（如 3 位银行账号、短于 8 位的发票号） | **不足即全掩码**（输出 `****`，不回退原文、不报错） | 边界形态留给后续批次裁决；回退原文 = 泄露，抛错 = 拖垮主流程 |
| **P5E-4** | 未知 `category` | **显式抛 `ValueError`** | 静默回退原文是最坏失效形态（"以为脱敏了其实没有"） |
