### 12.1 重复实体清理（`fix_dup_entities.py`）

### 12.2 归因闸门落地（`agents._grounded_citations`）

## 13. 批次 E 收尾（续）：召回侧修复 —— 组内**并列排序键**（用户决策：闸门不退，修召回）

§12.4 判定「Q11 / Q12 是召回问题，闸门救不了」，本段是该结论的落地。
**结论先行**：修的不是"条数"，是**并列时的排序键**；条数只从 20 提到 32
（字符 10.6k → 15.0k），归因 75% → **100%**、库内答对率 0.83 → **1.00**。

### 13.1 先量后改：抬保底这条路是死路（e12 / e15，¥0）

| 项 | 实测 |
|---|---|
| 语料规模 | **13 篇文档 / 205 chunk**（不是先前以为的 8 / 46） |
| 保底公式 | `floor = limit // 文档数` ⇒ limit=20 只保底 **1 条/文档** |
| Q11（LV0001）依据 | 组内第 **3**/11 ⇒ floor ≥ 3（limit 39，字符 21.5k） |
| Q12（SO-2026-0912）依据 | 组内第 **4**/8 ⇒ floor ≥ 4（limit 52，字符 30.0k） |
| Q09（张伟）依据 | 组内第 **19**/40 ⇒ floor ≥ 19 ⇒ limit 247 ⇒ **注入 204 条 / 13.0 万字符** |

⇒ 抬保底的代价由**排名最靠后的那题**决定（张伟排第 19），不可行。

### 13.2 中间轮次：`limit=52` 跑出了「净收益 0」（不粉饰，登记在案）

按"抬保底"落地到 52 后真实重跑 14 题：Q11 / Q12 **得救**，但 **Q09 / Q10
反被误伤为拒答** ⇒ 库内仍是 10/12，只是把"能答的题"从 A 换成 B。
顺带排除了一个错误假设：e13 实测 **20 条 ⊆ 52 条（丢失 0 条）**，
所谓的"保底挤掉余量"**不存在**。该轮结论是**回滚思路**，代码未保留 52。

### 13.3 病根：**并列退化**（e15 / e16）

CSV 派生片段的 `MENTIONS` **大量并列**（employees 表 40 条片段全是 1）
⇒ 组内排序 `(-mentions, chunk_id)` **退化为 chunk_id 字典序**，等价于**随机抽样**；
而 Q09 / Q11 / Q12 的依据**恰好都是各 CSV 的首行**。
⇒ 并列时改按 `char_start`（**文档原始顺序**）排，"每组前 N 条"= 文档开头，
首行必然在场。e16 离线验证：**limit=20 即可 12/12 全覆盖，字符 9.6k**。

### 13.4 落地改动

| 处 | 改 |
|---|---|
| `select_evidence_chunks` | rows 升为**五元组**（+`char_start`）；组内 `(-mentions, char_start, chunk_id)`；余量补齐同样加 `char_start` |
| `_QUERY_EVIDENCE_CHUNK_INDEX` | 多回一个 `coalesce(c.char_start, 0)`（索引行很便宜） |
| `_EVIDENCE_CHUNK_LIMIT` | 20 → **32** |
| `tests/test_evidence_selection.py` | 元组同步升维 + 新增 2 条口径用例（并列按文档序 / 热度仍压过文档序） |

**为什么是 32 不是 20 / 26**：`26` 恰好是**最差档**——floor=2 ⇒ 13×2=26 ⇒
**余量归零**，制度文档（3 条片段）只拿到 2 条 ⇒ Q05/Q06/Q07/Q08 依据全丢
（e16：覆盖掉到 **8/12**）。20（floor=1 + 余量 7）与 32（floor=2 + 余量 6）
都是 12/12；取 32 是因为 20 靠 7 条余量侥幸覆盖制度文档，换语料更易塌。
