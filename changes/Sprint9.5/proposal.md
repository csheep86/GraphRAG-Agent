# Sprint 9.5 · 考勤业务域 DEMO（提案）

> **状态**：Proposed
> **提出日期**：2026-09-27
> **决策来源**：用户 2026-09-27 拍板四项（见 §6 决策记录）
> **性质**：**业务域变更 + 演示形态变更**，不是语料替换

---

## 1. Why：现有演示打不中客户痛点

现有 `v1.4.0` 演示链路是「上传债券/年报 PDF → 建图 → 问答 → 关联交易疑点」。它对目标客户（**制造企业**，如 `docs/demo.html` 中的恩仕卫浴）**零共鸣**：

| 现有演示 | 客户感受 |
|---|---|
| 「招商蛇口的法定代表人是谁」 | 我是造卫浴的，不关心 |
| 「共享注册地址 → 关联交易疑点」 | 我没有这个场景 |
| 语料是金融公开文档 | 与我内部系统无关 |

`docs/demo.html` 里那句才是真痛点：

> **HR 处理时长：原 18 分钟 → 现 1 次点击确认**

客户要的是：**一条考勤异常，系统自动跨 HR / 门禁 / 工单 / 定位 四个系统取证并归因**。

**演示无效 = 前期工作无法转化为商机**。本变更的目的不是"换个语料"，是**把系统改造成能演示企业真实业务域的形态**。

---

## 2. What：目标形态（对齐 `docs/demo.html` 考勤域）

三个子页，**全部跑真链路**：

| 子页 | 演示内容 | 打中什么痛点 |
|---|---|---|
| **政策问答** | 「我是售后工程师，上周六在武汉出差处理工单，这算加班吗？」→ 答案 + **推理路径链** + 判定结论 | 制度问答**不是**关键词检索，是**沿图谱多跳推理** |
| **异常归因** | 张伟 10-14 缺卡 → **原因排序（含置信度）** + **跨系统证据链** + 建议动作 | 原来 HR 跨 5 个系统查 18 分钟 |
| **合规预警** | 全公司扫描 → 工时/加班/调休风险清单 + 依据 + 建议动作 | 发薪前 7 天提前发现，避免劳动争议 |

## 4. 数据方案：可复现的仿真语料

> **口径**：全部为**仿真生成**，用于演示与链路验证。**不得**在任何交付物中称为"真实客户数据"。
> **规模**：约 40 名员工 × 1 个月 ≈ **千级节点量**（相对 `demo.html` 的 48620 实体是**真实规模**，演示语料刻意取小以保证可复现与可核查）。

### 4.1 制度文档（走 M1 解析 + M2 抽取）

> 已落地于 `demo/attendance/policies/*.md`（源）+ `corpus/*.docx`（M1 消费）。
> **形态说明**：M1 的 MIME 白名单只收 PDF / DOCX / CSV，Markdown 不在内 ⇒ 生成器用标准库 `zipfile` 手写 OOXML 把 `.md` 转成 `.docx`（零第三方依赖，网络受限环境下可用）。

| 文档 | 覆盖条款 |
|---|---|
| 《员工考勤管理制度（2026 版）》 | 出勤定义、缺卡认定、迟到规则 |
| 《工时制实施细则》 | 标准 / 综合 / 弹性三种工时制的适用岗位与时段 |
| 《加班与调休管理办法》 | 加班认定、200% 计付、调休期限 |
| 《外勤与出差考勤补充规定》 | 外勤出勤依据（定位 + 工单 + 审批），**门禁不作为唯一判据** |

> 这四份文档**刻意包含版本更替**（如 2025 版「外勤需手工补卡」→ 2026 版「自动补卡」），用于顺带验证 **ADR-0005 时效知识**——同一问题按不同时点问，答案不同。**这是白捡的演示点**。

### 4.2 业务数据 CSV（走新增的确定性入图器）

| 文件 | 内容 |
|---|---|
| `employees.csv` | 员工 / 部门 / 岗位 / 工时制 |
| `attendance_records.csv` | 打卡记录（含缺卡、迟到） |
| `shifts.csv` | 排班班次（含连班） |
| `leave_requests.csv` | 请假 |
| `overtime_records.csv` | 加班单 |
| `business_trips.csv` | 出差审批 |
| `work_orders.csv` | 售后工单（**跨域**：考勤 ↔ 售后） |
| `location_records.csv` | 移动定位 |
| `access_records.csv` | 门禁刷卡 |

### 4.3 埋设的演示用例（与 `demo.html` 一致）

| 用例 | 数据形态（已埋设） | 期望结论 |
|---|---|---|
| **E001 张伟** · 售后工程师 / 综合计算工时制 | **10-16（周五）**缺卡、当日**无门禁**、**前一日有门禁**（构成对比）；出差审批 10-16~10-18 武汉；工单 `SO-2026-0912` 当日 09:40 派单 10:22 闭环；定位 09:58 / 13:20 均在武汉光谷 | 缺卡 → **外勤出勤成立**，自动补卡 |
| **E001 张伟**（续） | **10-17（周六，休息日）**工单 `SO-2026-0913` 09:15 派单 11:40 闭环 | 休息日出勤**不当然构成加班**，须结合月度累计判定（制度二第七条） |
| **E002 李静** · 产线操作工 / 综合计算工时制 | 月排班 **216h**（10 天 12h 连班 + 12 天 8h），月标准 174h ⇒ 加班 **42h**；连续出勤 **22 天** | **月加班超限**（42 > 36h，高）+ **连续出勤无休**（中） |
| **E003 王强** · 研发工程师 / 标准工时制（弹性） | 10 月 **7 次**核心时段（10:00–16:00）未在岗 | **弹性时段越界**（阈值 5 次，中） |
| **E004 陈敏** · 客服专员 / 标准工时制 | 月加班 **22h**，已调休 **0h** | **调休未消化**（高） |

> **日期已核对星期**：10-16 = 周五（工作日，才有"缺卡"），10-17 = 周六（休息日，才有"算不算加班"）。
> 初稿曾把缺卡日误设为 10-14，但 2026-10-14 是**周三**，且休息日本无打卡义务、不会生成缺卡记录——已纠正。

## 5. 设计要点（五个必须新建的能力）

### 5.1 考勤本体（M6 折中：只做 schema 配置化）

**只建** `ontology_schemas` 表 + 一份考勤 schema 种子；**不做**冷启动 GUI / 校正界面 / 增量重算（保持 S12）。

**实体类型**（`entity_types`）：
`EMPLOYEE` / `DEPARTMENT` / `POSITION` / `WORK_TIME_SYSTEM` / `POLICY_CLAUSE` / `ATTENDANCE_RECORD` / `SHIFT` / `LEAVE` / `OVERTIME` / `BUSINESS_TRIP` / `WORK_ORDER` / `LOCATION_RECORD` / `ACCESS_RECORD`

**关系类型**（`relation_types`）：
`BELONGS_TO` / `HAS_POSITION` / `APPLIES_WORK_TIME` / `HAS_ATTENDANCE` / `HAS_SHIFT` / `SUBMITTED_LEAVE` / `ACCUMULATED_OVERTIME` / `ON_BUSINESS_TRIP` / `TRIP_FOR_ORDER` / `GOVERNED_BY` / `LOCATED_AT` / `SWIPED_AT` / `OCCURRED_ON`

> **守 M6 §3.5 验收 12**：schema 须经**确认**才写 `active`；未确认前用内置默认 schema 且不阻断。

### 5.2 结构化数据入图器（**新增**，接缝 8 扩展）

**现状缺口**：接缝 8（`external_data`）明确「**不建表、落地 `external_refs`、不进图谱**」。而考勤主体数据是 CSV ⇒ **必须新增」。

形式：**CSV 行 → 图谱节点/关系的确定性映射**（配置文件驱动，**不用 LLM**——结构化数据用 LLM 抽取是错配）。

```text
mapping.yaml: {csv_file -> node_label, columns -> properties, join_keys -> relationship}
```

> **不建新表**（延续接缝 8 范围纪律）；直接写 Neo4j，沿用 ADR-0002 `kg_version` 幂等键。

### 5.3 确定性规则引擎（**新增**）

**为什么不能靠 LLM**：`demo.html` 里「月加班上限 36h」「周工时 60h」「季度 108h」是**精确数值**，纯 LLM 生成**必然编数**，且违反 F3（无溯源即拒答）。

| 规则 | 判据 | 等级 |
|---|---|---|
| 周工时超限 | **标准工时制**岗位周实际工时 > **40h** | high |
| 月加班超限 | 月累计加班 > **36h**（劳动法第 41 条） | high |
| 调休未消化 | 已产生调休额度且已调休 = 0，季度剩余 < 30 天 | high |
| 弹性时段越界 | 弹性制岗位月度核心时段（10:00–16:00）未在岗 > 5 次 | medium |
| 连续出勤无休 | 连续出勤 ≥ 12 天 | medium |

> **口径分岔（实现时必须区分）**：
> - **综合计算工时制**（李静）：加班 = 月累计排班工时 − 月标准 **174h**（制度二第七条，**按周期核算**）；
> - **标准工时制**（陈敏）：加班 = 已审批加班单累计（制度三）。
>
> 演示稿 `demo.html` 的"周工时 60h""季度 108h"**不予采用**：前者与法定 40h 冲突，后者无法律依据。

**规则值从图谱 `POLICY_CLAUSE` 读取**（不是硬编码）——这样制度改了规则自动变，**顺带演示"制度可配置"**。

### 5.4 异常归因（复用 M4，扩两处）

**M4 现状**：`affiliation_suspicions{type, severity, entities, evidence}` —— 有证据链，但**无"原因排序 + 置信度"**。

**扩展（不改既有语义，只加）**：

| 扩展 | 内容 |
|---|---|
| `suspicion_type` 域化 | 由金融枚举（shared_address…）扩展为**按本体域可配置** |
| 新增 `causes` | `[{reason, confidence, evidence[]}]`——**原因排序 + 置信度** |

**置信度来源**：**确定性证据匹配度加权**（如：出差审批 ✓ + 工单闭环 ✓ + 定位匹配 ✓ → 87%），**禁止 LLM 生成置信度**。

### 5.5 推理路径（M3 扩展 + 前端新增）

M3 现有多跳 Cypher，但响应**无** `reasoning_path`。新增：

```json
"reasoning_path": [
  {"node": "张伟", "label": "EMPLOYEE"},
  {"rel": "HAS_POSITION", "node": "售后工程师"},
  {"rel": "APPLIES_WORK_TIME", "node": "综合工时制"},
  {"rel": "ON_BUSINESS_TRIP", "node": "武汉出差"},
  {"rel": "TRIP_FOR_ORDER", "node": "SO-2026-0912"},
  {"rel": "OCCURRED_ON", "node": "休息日出勤"}
]
```

> **数值结论由 §5.3 规则引擎给出，LLM 只做自然语言组织**——这是本项目「确定性优先」（ADR-0005 同款思路）的延续。

## 7. 风险

| # | 风险 | 缓解 |
|---|---|---|
| **R9** | 仿真语料被误认为真实客户数据 | 所有产物（语料目录 / README / 演示脚本输出 / 前端页脚）**标注「演示语料（仿真）」**；禁止在任何交付话术中称为真实数据 |
| **R10** | 确定性规则引擎是**新增架构件** | 现有 M3「LLM 生成答案」路径不覆盖；需明确规则引擎与 LLM 的职责边界（规则出数值，LLM 出措辞） |
| **R11** | 跨域（考勤 ↔ 工单）需售后域最小数据 | `work_orders.csv` 只取与考勤归因相关的字段，**不实现售后域其他能力** |
| **R12** | 与 S9 冲突 | S9 正在做四源对齐 + 时效改造；本变更**独立立项**，不挤占 S9 任务 |
| **R13** | 演示规模过小显得"玩具" | 演示语料刻意取小是为了**可复现与可核查**；`demo.html` 的大数字属**目标形态**而非当前承诺——**不得**把 48620 实体写进任何交付口径 |

## 8. 验收口径（对齐 A15 / F3）

1. **零假数据**：图谱中每个节点必须能回溯到某份语料的具体行/页；**禁止**硬编码演示答案
2. **引用覆盖率 100%**：政策问答每个事实句必须有 `POLICY_CLAUSE` 溯源，否则**拒答**（不能为"看起来能答"放松）
3. **数值可核查**：合规预警的每条风险必须给出**计算过程**（如"62h = 排班 6 天 × 平均 10.3h"）
4. **一条命令复现**：`demo_rehearsal.py --domain attendance` 全绿
