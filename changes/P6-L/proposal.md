# P6-L · 让哨兵**第一次真触发**——用现成的更大语料（¥0 / 不判分 / 不造语料）

> **日期**：2026-10-06 ｜ **上游**：[`changes/P6-K/`](../P6-K/)（哨兵已建、本语料 213/213 零损失）
> **用户裁决（2026-10-06）**：下一批走 **①「更大 + 更难语料」**；判分**暂不定**，
> **本批只做不判分的语料部分**（造语料 + 跑机械量）。

---

## 0. 一句话

**原计划是"造一份更大的语料"；开工侦察发现图里已经躺着一个 4.6 倍的现成语料**
（`affiliation-demo-v2` = **988 chunk**），且**生产 500 采样只覆盖其中 355 / 988 = 35.93%**
⇒ **不必先花 ¥ 造语料**，本批用它在真机上把哨兵第一次喊出来，拿到真实劣化数据后
再决定要不要造、以及造多大。

## 1. 为什么改动作（不是换方向，是同路的更省前置）

| 原计划（用户裁决 ①） | 本批（收敛后） | 省掉什么 |
|---|---|---|
| 造更大 + 更难语料 ⇒ 重抽入图 ⇒ 重判 | **用现成的更大语料**跑机械量 | 语料生成 + 抽取入图（**¥**）+ 全量重判（**判分人力**，已裁决后置） |

**为什么这个前置必须先做**：如果先造语料，会发现「判据口径（判分谁做 / C1 是否复活）」
还没裁 —— 那是拿最贵的动作去喂一个还没定的判据。反过来，本批 ¥0 就能拿到
「规模风险是否真的兑现 + 劣化到什么程度」，这两个数正是"要不要造、造多大"的判据。

## 2. 已验事实（真图量过，**不是**读代码推的）

```
$ docker exec graphrag-neo4j cypher-shell -u neo4j -p graphragdev "..."

kg_version              chunks   实体    文档   org_id
attendance-demo-v1      213      2805   —     00000000-0000-4000-8000-000000000001
affiliation-demo-v1     128      —      —     —
affiliation-demo-v2     988      1268   5     5dea8f62-0c67-579a-9509-8b4ce98eadea
```

| 量（对 `affiliation-demo-v2`） | 值 |
|---|---|
| chunk 总数 T | **988** |
| 版本内实体总数 N | **1268**（Invoice 500 / Contract 200 / Subject 120 / Address 116 / LegalPerson 116 / Phone 116 / Voucher 100） |
| **全量 1268 实体**能覆盖的 chunk | **988 / 988 = 100%** |
| **取前 500 实体**能覆盖的 chunk | **568 / 988 ≈ 57.5%** |

⚠️ **568 是粗估，不是产品口径**：那条 Cypher 用的是 `LIMIT 500`，而生产采样是
`fetch_all_subgraph`（按 `entity_type` 保底取 500）。**真值由本批的脚本出**，
这里只用来判断"值不值得做"（结论：值得——差了 420 条，不可能是噪声）。

**与 attendance 对比 ⇒ 差异的根源不是"规模"本身，是「提及密度」**：

| 语料 | chunk | 实体 | 每 chunk 平均被几个实体提及 | 500 采样够不够 |
|---|---|---|---|---|
| `attendance-demo-v1` | 213 | 2805 | ≈ **13.2** | ✅ 够（100%） |
| `affiliation-demo-v2` | 988 | 1268 | ≈ **1.28** | ❌ 不够（**35.93%**，真机实测） |

⇒ 这正好补上 P6-K 缺的那一半：P6-K 只证明了「本语料零损失」，
而**"零损失"是因为本语料提及密度高达 13**，换一份密度正常的语料，**同一个固定预算立刻开始丢**。

## 3. 本批裁决

| # | 裁决 |
|---|---|
| **L-D1** | **本批不造语料**。现成 `affiliation-demo-v2`（4.6×）已足以触发哨兵；先拿真实劣化数，再裁"要不要造 / 造多大" |
| **L-D2** | **只出机械量**（U / S 两档候选数、窗口完整率、撞 `index_limit` 次数），**不判分**（用户裁决：判分口径后置） |
| **L-D3** | 诊断脚本加 `--kg-version` / `--org-id` ⇒ 可对**任意版本 / 租户**诊断。现在它写死取 active 版本 + 单一 org —— 这是常驻脚本的**通用性缺口**，本批顺手补齐（它属于"让诊断可复跑"这条需求） |
| **L-D4** | 新增一条**能在 CI 上真跑**的用例：CI 会先导入 `affiliation-demo-v2`（见 `ci.yml`「导入受控种子语料」）⇒ 该用例在 CI 上**不 skip** ⇒ 哨兵从此**每次 CI 都被真实语料验一次**。这补掉 P6-K 的唯一未验证项（此前只有单测合成场景作证） |
| **L-D5** | `affiliation-demo-v2` 是**疑点检测语料**（C2-a / C2-b），**不是问答语料**（无 40 题 gold）⇒ 本批**只出语料级机械量**，换版本时脚本**默认不跑题集**（不同域的题集放上去没有意义，反而会造出一个"看起来有数、其实不相关"的表） |

### 3.1 L-D3 的具体行为（避免歧义）

| 参数 | 默认 | 说明 |
|---|---|---|
| `--kg-version` | 无 ⇒ 取 active 版本（**与 P6-K 行为完全一致**） | 给了 ⇒ 直接诊断该版本，不走 `fetch_active_kg_version` |
| `--org-id` | `00000000-0000-4000-8000-000000000001` | 换版本时**必须**一起给（v2 的 org 不同） |
| 逐题表 | `--kg-version` 给了 ⇒ **默认不跑**；`--with-questions` 可强制 | 理由见 L-D5；汇总段据此打印 `N/A` 而不是空表/除零 |
