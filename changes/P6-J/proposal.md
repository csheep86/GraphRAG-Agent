# P6-J · 决策文档：图侧「question 不参与检索」怎么办

> **日期**：2026-10-05 ｜ 前序：`P6-I`（rubric-v2，C1 = 8.82%，距阈值 1.18pp）
> **性质**：**诊断已完、方案待选** —— 根因已用代码 + 实测量化坐实，但修法牵涉 C1 的归因纯度，需你拍板
> **一句话**：图侧证据是「**与问题无关**的结构性窗口」⇒ Q20/Q22/Q26 的目标条文**根本没进候选**；
> 修它必须让 question 参与检索，而**那会让图侧沾上 dense 的能力 ⇒ C1 测的东西随之改变**。这个代价要先说清。

---

## 1. 根因（已坐实，不是推测）

### 1.1 链路：question 从头到尾不参与

```
question
  └─ fetch_all_subgraph(node_limit=500)
       └─ select_subgraph_nodes()   ← 按【实体类型保底 + 度数降序】采样，headers：`question` 不在入参里
  └─ entity_ids = [子图里的 Entity 节点 id]（+ 少量锚点）
       └─ fetch_evidence_chunks(entity_ids=...)
            └─ select_evidence_chunks(rows, limit=32)  ← 按【每文档保底 + MENTIONS 降序 + span 优先】
                                                        headers：入参只有 (chunk_id, doc_id, mentions, spans, char_start)
                                                        ⇒ **没有 question**
```

两个采样函数（`:func:`select_subgraph_nodes`` / `:func:`select_evidence_chunks``）都是**纯结构排序**。
`graphs.py:93` 那段"反面教材"注释自己也承认了这一点：

> 本架构下 ``question`` **不参与检索**（候选集是结构性窗口），依据进不来就**没有任何补救路径**。

### 1.2 实测量化（复现脚本直接调用产品的两个纯函数 + 产品自己的 Cypher）

```
实体总数 2805 ⇒ 子图采样 500
候选 chunk 213 条 ⇒ select_evidence_chunks(limit=32) 选出 32 条

Q20 月标准工时   chunk-cc75924988e4  ❌ 被切掉
Q22 审批程序     chunk-eb5f28fb5e2a  ❌ 被切掉
Q26 预警处置     chunk-80577ef6ea9a  ❌ 被切掉

选出的 32 条文档分布：14 条「未挂文档」+ business_trips/employees/overtime_records/…
等 9 份 CSV **各恰好 2 条** ⇒ 制度条文全部挤在「未挂文档」这一组里争排名，输给了热度更高的片段。
```

（复现脚本用产品自身的 Cypher 与纯函数，没有重写规则 ⇒ 验的是产品行为，不是我的复述。）

### 1.3 为什么受影响的恰好是这三道题

Q20「月标准工时是多少小时」/ Q22「不定时工作制需要履行什么程序」/ Q26「高等级预警多久内处置」
—— 三题都是**纯概念性提问**，句中没有员工号 / 单号 / 日期等实体锚点
⇒ 结构性采样没有任何凭据可依 ⇒ 目标 chunk 在候选里，却排不进 32 条。

而 **dense 侧恰恰把这三题都答对了** —— 因为 dense 就是按语义相似度直接命中。同一份语料、同一个 LLM、
同一份 prompt，唯一变量是检索方式 ⇒ **这 1.18pp 的差距，来源就是这里**。

## 2. ⚠️ 真正的岔路：修它要不要付归因代价

C1 的定义是「**图侧**相对 **dense 侧**的增益」，目前：

- `RETRIEVER_GRAPH = "graph_mentions"`（结构性窗口）
- `RETRIEVER_BASELINE = "dense_top_k"`（按 question 做向量召回）

⇒ **「question 参不参与」恰好就是两侧唯一被 locked 的发展变量**（其余都冻结了：同池、同 k、同模型、同 prompt）。

所以：

> **在图侧引入任何形式的 query 相关性，都是在把 dense 的能力搬进图侧。**
> 系统会因此变好、分数会因此上升，但 C1 从此测的是「图结构 + query 重排」而不是「图结构」。

这不是要不要作弊的问题（改产品≠作弊），而是**读数含义变了**：
以后看到 C1 = X%，说不出其中多少归图结构、多少归重排。若不显式登记，就是一处**隐性归因漂移**。

⇒ 诚实做法只有一种：**改的同时把 `RETRIEVER_GRAPH` 这个标识一起改掉**，让报告的新指在它名下，
与旧的 `graph_mentions` 数字不可混用（与 P6-D 删 `QSET_CORPUS_LAYER` 常量同一个道理：
换个名字就能把一件东西说成另一件，而没有任何机器能证伪）。

## 3. 四条修法（含一条我认为不该走的）

| | 做法 | 能否救这三题 | 归因代价 | 其它代价 |
|---|---|---|---|---|
| **M1** 轻量 lexical 重排 | 在现有候选上按 question 与 chunk 的**词面重叠**打分，命中者优先占名额 | ✅ | **中**：question 参与了，但不是向量语义 | 无新依赖；可控、可单测 |
| **M2** 图侧装 embedding 重排 | 候选按 query 向量相似度重排 | ✅✅ | **最大**：图侧实质变成 hybrid+dense ⇒ **C1 失去意义** | 图侧引入 embedding 依赖 + 每次问答多一轮向量化 |
| **M3** 抬保底 / 抬条数 | 把 32 提到 60+ | 可能 | 无 | ❌ **不采纳**：`graphs.py:93` 明写这是反面教材（20/26/32 都是实测选过的，26 恰好最差）；治标且随语料反复失效 |
| **M4** 抽取阶段补概念实体 | 让「月标准工时」在 M2 抽取时落成 REGULATION/条款实体 | 部分 | **小**（仍是图驱动） | 依赖抽取质量；要重新入图；见效慢 |

## 4. 我的建议

1. **采纳 M1（轻量 lexical 重排）**。理由：恰好补上「question 完全不参与」这个致命缺口，
   又不给图侧装 dense 引擎 ⇒ **C1 保住大部分归因**。它是这四个里唯一"治本但不过量"的。
2. **同时改 `RETRIEVER_GRAPH` 的标识**（如 `"graph_mentions+lexical_rerank"`），并在 `comparability_error`
   里核对两侧仍同源 ⇒ 让这次提升**显式地**记在新名字下，不与历史数字混用。
3. **M2 先别做**。真到要用 embedding 重排那天，应该连带 reconsider C1 是否还有意义，而不是悄悄加。
4. 修完之后：**全部 40 题两侧重判**（这次动的是检索 ⇒ 注入片段变了 ⇒ 答案变了 ⇒ 旧判分全部作废）。
   ⚠️ P6-I 那 8.82% 是在旧链路上测的，**不得与本批的数字直接相减**。

## 5. Non-goals（冻结）

1. **不校准阈值**（属 ⑤）；本批只管把依据送进 Prompt；
2. 不改 C1 的增益公式，不动 rubric（rubric-v2 已定）；
3. 不删敏感 Winter / 不改题面 / 不改 40 题组成；
4. 不引入新第三方依赖（尤其不给图侧引入 embedding ⇒ 那会把 M1 变成 M2）；
5. 不改 prompt 版本、不改生成模型、不改 top-k 配额（32 是实测值，动它属 M3，已否决）；
6. 不顺手修 H6 403 / 制度入图器自检恒 FAIL / P7-B / G-12 / MANIFEST 语料统计过期；
7. **不把 `RETRIEVER_GRAPH` 的名称改回去**（改名即换二代联系 ⇒ 历史数字作废是**必须**的结果，不是副作用）；
8. 本批的修复必须能被**反向验证**：撤掉修复，这三题应当**重新被切掉**（否则验证的是别的东西）；
9. 不动 ingestion / 写入侧：诊断已确认三条目标 span **全部在库**（缺的是读取侧，不是数据）。
